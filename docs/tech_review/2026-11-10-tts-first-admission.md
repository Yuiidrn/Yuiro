# 逐句翻译完成顺序不应决定首句合成优先级

VoicePipeline._feed原先为每句创建并发任务，任务内先await出口语言转换，再调用TTSTaskManager.enqueue。manager虽然按seq保序交付，但两路合成信号量按实际抵达顺序获取：第2/3句先译完时先占满名额，第1句译完反而排在后面。保序输出不等于有序入场，首句延迟被后句合成时长放大。

本次用每句独立的asyncio.Event建立入场链。翻译在链外并发，转换完等待前一句入场；取得资格后先传递事件，再调用enqueue。首句优先取得空闲信号量，后句仍可使用第二路；后续顺序依靠asyncio信号量等待顺序及原有manager seq交付。没有让每句等待前句合成结束，也没有并行播放不同句子。

空标点/引号/Markdown残片在翻译前清理为无声空序号，manager也拒绝独立纯符号请求。没有压缩或改写正常回答，数字、拉丁文、中日韩字均保留；纯emoji片段不会单独合成。句序不因跳过请求而移动。

取消开放句流时，旧_feed可能仍在async for中，尚未进入gather，已经创建的翻译子任务原先可能脱离清理。本次finally取消并join所有pending，外层也join被取消的feed_task，再按既有manager所有权清理。测试覆盖该时序且保留CancelledError传播。

确定性fixture显示首段中位交付186.90→62.26ms，但全段186.93→218.51ms：这是首句体验优先、保留两路并发的取舍，不能只报前者。生产Fish六次短日语HTTP实测依然出现完整返回1.79–5.31秒，调度修复并未消除供应商/网络和整句下载等待。
