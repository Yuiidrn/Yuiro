# Windows 官方客户端精确选歌与角色归属复盘

关联 [实施与验收报告](../plan/netease-exact-client-selection.md)，日期 2026-10-24。用户最终确认：“原版正常，最后无残留”。本轮延续现有 Runtime，以 Monody 原版 `36308916` 完成局部接入。

## 协议投递、精确定位与播放是三个完成条件

前一轮的 `orpheus://song/ID` 请求没有可靠定位证据。调研另一个 Windows 项目的实现发现，当前客户端接收的是编码后的 JSON 播放命令。改用 `type=song,id=<明确数字>,cmd=play` 的 base64 URI，仍通过官方注册的 exe、独立参数和明确工作目录投递，没有把任意 URL 或 shell 命令开放给调用者。

协议编码正确只证明请求形式正确，不能自己把发送出去的 ID 填回响应当作“核验成功”。因此补了独立的当前歌曲读回：客户端当前资源 ID 等于请求、非试听、曲名与 SMTC 一致、状态 Playing，全部满足才告诉 UI 已播放。失败没有换 API、没有换版本、没有启动 mpv 兜底。

冷启动的失败说明定位和起播还必须分开确认。客户端短时没有页面、没有 store 或没有 SMTC，会依次进入不同准备阶段；有时已经定位到 Monody，却仍 Paused。最初只等 Playing 会超时。修正后，仅在独立 ID 已匹配时明确请求 Play，再回读状态。独立诊断冷启动约 9.9 秒，结果卡冷启动约 13.9 秒；不能把这种启动成本藏在暖启动数字里。

## 复用链路，只新增一个窄适配器

```text
独立 ResultCard：用户明确选播放器
  → 桌宠 App：拥有候选、角色/会话、请求序号
  → 原 Engine WS：media:play / media:control
  → official_client：校验精确 ID 与短生命周期播放归属
  → NativeBackend
       ├─ 固定编码命令：官方 exe
       ├─ 固定本机状态投影：客户端当前歌曲 ID
       └─ 现有精确 SMTC：Play/Pause 和状态确认
```

没有第二套 Agent、Session、Avatar 或播放器 Runtime。`netease/official_client.py` 只负责这个执行适配的锁、在途请求和归属，角色取消仍由现有 `_quiesce_character` 收敛。原 `netease/client.py` 的 CLI 登录/搜索入口保留，临时命名冲突已恢复，最终无内容差异。

播放器选择是本次点击的确定意图，不是全局自动后端策略。普通歌曲行与“桌宠播放器”仍走原 mpv 链路；“网易云客户端”才进入官方适配。官方单曲能力稳定后开放按钮，歌单/队列没有顺手迁入新的内部接口。

## 归属必须比系统当前播放状态更严格

仅知道 cloudmusic.exe 正在播放，不能说明它属于当前角色。本轮将所有者绑定角色 ID、revision、session ID、唯一 playback_id、song ID，再由引擎核验前端身份。新一次选歌会更换 playback_id，旧卡片和旧 WS 控制不能继续控制它。

角色切换先使旧 epoch 失效，再取消旧工作；OS 投递线程若已启动，先收敛回执，检查可能已播放的同一 ID，确认暂停后才跨过角色边界。无法读取且可能仍播放时不把错误吞掉；若客户端已退出，则归属可以直接释放，不应无限阻塞角色切换。

用户手动切到另一首歌时，只释放旧归属，不暂停新歌。这条回归测试和“在状态读取期间切换角色，不得再发控制”的测试，针对的是旧动作晚到的问题。适配器互斥锁与执行前后的核验保证自己的任务不抢控制；同一客户端仍可能接受用户手动操作，状态不一致时必须报未确认，不能声称所有并发人工操作都能被桌宠锁住。

既有自管 Stop 测试也被保留：官方音乐正在播时，自管 netease_control 的 Stop 没有转去控制它。通用系统媒体工具只在用户明确指定对应应用时使用，不能拿来补偿自管播放器空闲。

## 状态连接的边界和改良

参考项目用本机 Chromium 连接读取内部状态，但其示例模块编号在本机版本已经变了。直接照搬固定编号会调用错误模块。本轮从已加载模块中识别符合当前 store 结构的对象，只返回当前 ID、歌名、歌手、时长和试听标志，没有读取账号、cookies、完整歌单或历史，也没有引入参考项目的搜索、队列或任意执行接口。

连接前检查 TCP listener 属于注册的 cloudmusic.exe，只允许 IPv4 回环 `127.0.0.1:9223`，主页面必须唯一且符合固定 URL，WebSocket 主机/端口/路径再次验证。最初每次用 PowerShell 查询端口，给状态读取增加了开销；后改用 Windows GetExtendedTcpTable 与进程路径查询，实机单次状态投影测得约 255 ms。端到端仍包含 SMTC、客户端准备和界面确认，不能把 255 ms 当作完整点歌耗时。

HTTP 不走环境代理，不跟随到其他地址；外部调用者不能提交 JavaScript。它仍是当前客户端版本的内部状态适配，升级后可能失效。CDP 本身并非受鉴权保护的沙箱：限制本适配自己的方法，不等于限制所有本机进程能通过这个端口做什么。因此只在显式官方选择时启用回环连接，不改客户端持久设置；已有普通启动的客户端不会被自动强杀重启。

## 暂停与状态同步不能等 LLM

官方 Stop 的历史实测结果仍有效：接口可返回接收，但状态不变，can_stop=false。本轮 UI 只显示“暂停/继续”，没有隐藏 Stop→Pause 映射，也没有假进度条。

播放选择仍走原串行工作队列，保持与点歌回合的互斥。暂停/继续和状态查询则从 WS 接收路径派发为受角色任务集合管理的控制任务，避免排在长 LLM 回合之后。它们通过同一个适配器锁、所有者和 epoch 校验，不绕过角色取消。

前端只在相关卡片与归属存在、无在途请求时每 5 秒同步状态；request_id 拒绝过期回复。独立窗口的新动作继续被 sender/key/index 围栏约束；控制动作还必须存在当前播放归属。收起、切换和晚到轮询不会复活旧选择。实机视觉检查后，状态文字单列，避免把“播放中”拆成两行；通道不可播的卡片文案直接告诉用户可选官方客户端。

## 验证分层与遗留

本轮 Python **904 项通过，无跳过**；前端类型检查、生产构建，以及既有独立窗口、Alpha 轮廓、C0 异步隔离检查通过。新增 21 个适配回归用例，包含参数、归属、试听、手动换曲、取消、关闭客户端、连接地址和定位后 Play 等风险。

真实 API 候选投影后，经 Windows 原生鼠标点击独立结果卡，实际 Engine 与官方客户端完成两角色播放、暂停、继续和双向切换。冷启动另测；用户听感确认。这个链路不是伪造音频或截获播放，而候选投影也没有冒充本轮的 LLM 搜索调用。最终暖启动复验与全量测试并行，耗时应按验收报告的具体条件阅读。

不承诺其他客户端版本、任意曲库权益、真正 Stop 或可靠进度。后续优先观察冷启动和状态不一致的真实样本，再决定是否扩充兼容适配；暂缓客户端队列编辑、客户端私有搜索、大型常驻桥进程和 Runtime 重构。
