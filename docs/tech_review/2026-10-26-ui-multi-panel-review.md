# 三面板并存、空位选择与实机验证（2026-10-26）

## 从状态覆盖定位到布局问题

“长回复、选歌和来源同时出现”首先暴露的是状态所有权问题。原来的 `resultCard` 同时承接 `song` 和 `source`，即使窗口布局足够宽，也只能显示最后到达的一类结果。因此先在 `App.vue` 增加 `sourceCard`、独立计时和清理，再用原有按需创建的呈现窗口承载来源。保留单一 Engine 连接，来源窗口不连接引擎、不拥有音乐播放状态。

`clearResultCard()` 仍代表角色生命周期的全量结果清理；新增 `clearMusicCard()`、`clearSourceCard()` 分别处理单窗收起。来源过期和新回合清来源不再影响音乐候选或已拥有的官方客户端控制状态。角色/会话身份仍参与快照 key，旧窗口点击继续失效。

## 布局仍是小型纯函数

`main/detachedLayout.ts` 保留“先尝试用户首选侧，再尝试可用侧”的行为，只增加根据障碍边界生成的有限候选集合。候选对齐现有面板、模型和工作区边缘，统一夹紧在工作区内，并逐个排除模型及其他面板。扩展候选按离角色的距离排序，避免第一个角落碰巧可用就把第三张卡送到屏幕另一端。没有引入求解器、原生渲染框架或新的 Runtime。

窗口从原先两种增加到 `speech / results / sources`；来源窗口懒创建、复用 `DetachedApp.vue` 和 `ResultCard.vue`。`DetachedState.sources` 为可选字段，旧的只有回复/结果的快照仍可处理。主进程通过 sender 与 kind 匹配、key 和索引校验限制点击，来源额外拒绝所有播放器动作。

靠边时重排是预期行为。以绝对位移强行要求所有卡片始终与模型一致，会把“正确地换到上方”误判为不跟随。验收同时记录模型和各窗位移，并以工作区内、保护模型、彼此不相交和内容仍可操作判断布局正确性；不将一次重排描述成平滑动画。

## 实测方法与容易误判的地方

验收脚本 `scripts/diag/ui_multi_live.py` 使用真实 Agent 检索，再在实际窗口上检查长文本、四角、Alpha 内原生拖动、热更新和单独收起。Windows 几何采用物理像素；渲染器模型矩形按视口与原生窗口尺寸换算，允许 DPI 取整带来的微小差异。不会把窗口外的模型几何当成桌面上的可见角色。

第一次启动的是不带 watch 的开发壳。后续 TS 修改虽已在源码和构建中存在，运行中的 Electron 主进程仍使用旧布局，导致来源窗口隐藏。确认进程加载情况后仅重启该壳进程树，再带 `--watch` 启动；后续主进程修改与实机测试串行执行，避免重启打断正在验收的窗口。不要用纯函数测试通过替代实际主进程加载确认。

另一类问题来自模型输出：真实查询取得两类结果后，有时只回复简短开场或“文章已输出”。脚本先独立请求长正文，并在同角色/会话内保留刚取得的真实来源用于组合布局检查。仍不给正文时，另开显式 `--stress-long` 补验；只有这种模式才展开带标签的排版样本，回执明确记录原回复长度和样本模式。正常产品新回合仍清旧来源，测试保留不进入产品逻辑。此区别写进报告，避免用压力样本掩盖 LLM 行为不稳定。

## 回归与后续边界

实际主进程协调器测试新增三窗共存、不相交、来源动作正确转发及音乐控制拒收；来源独立过期测试验证不会清掉歌曲。既有轮廓命中、角色取消、UI 偏好及 TypeScript/构建检查继续执行。没有调整后端协议、角色音色、人设、模型资源或播放权益判断。

本次验收范围与回执见 [计划报告](../plan/ui-multi-panel-acceptance.md)。暂不宣称完成多屏混合 DPI 实机验收、连续拖动逐帧性能测量或卡片重排动画；当前有限候选计算成本很小，但没有以单次字号热更新观察值替代完整帧耗时指标。
