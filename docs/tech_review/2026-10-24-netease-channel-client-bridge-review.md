# 网易云通道权益、播放器归属与官方客户端桥接复盘

日期：2026-10-24。实施、实机证据和后续门槛见 [验收报告](../plan/netease-channel-client-bridge.md)。本轮是现有后端、NativeBackend 与结果卡的局部修补，没有替换 Runtime。

## 1. 三个不能混淆的事实

会员记录有效、某应用取得播放流、官方客户端能播放，是三件不同的事。真实 API 对照显示：同一 CLI/引擎 AppID、同一登录设备信息下，Monody 原版没有流，Remix 有 128 kbps 流；官方客户端又确实能播放原版，且用户听感确认。因此“没有地址→没会员/没版权”是错误推断。

新增 `netease/availability.py` 只把当前响应投影成安全状态，不新建 Rights Runtime。缺 playFlag 为 unknown，不能用 bool(None) 把它压成不可播；visible=false、缺完整地址与试听分别表示；vipFlag 等保留在白名单里，不能直接解释成用户的会员身份。搜索、工具、直连点击复用同一个判断。

错误码也需要保持语义：403 的应用拒绝不能触发登录失效提示或刷新循环；确切登录失效码才走既有登录恢复。没有尝试修改 AppID、device、trialScene 来伪装授权。

## 2. 精确意图不能交回模糊搜索

之前优先筛选 playFlag，再做歌曲匹配，可能将用户指定的原版挤走；队列路径又会把候选第一项直接入队。这会造成“有声音但版本错”的假成功。

本轮从三个入口收紧：

- 搜索保留服务端顺序与不可播原版；多候选或版本不确定时交用户选择。
- 卡片结构化 ID 直连，取回详情必须能确认同一数字 ID；未知/不符、仅试听或无流不播放，不重搜换版。
- 歌单与队列也用相同完整流判断；队列不能悄悄选候选第一项；当前曲目记忆只能指向实际加入播放的歌曲。

结果卡只增加通道状态和官方歌曲页按钮，没有新建一个播放器界面。独立窗口传 `action + index + key`，不允许子窗口随意提供另一首歌的 URL/ID；桌宠主窗口仍是数据所有者，角色切换和内容 key 仍约束新动作。按钮阻止冒泡，Enter 防止默认合成点击引起重复打开。

## 3. 播放归属比“尽量帮用户放出来”更重要

`netease_control` 仅管理引擎自管 mpv。没有播放、IPC 未知或 IPC 确认空闲，都不能自动解释为“接管用户网易云客户端”。这覆盖历史空闲转 SMTC 的策略；本轮不保留隐藏回退。

官方客户端试验通过现有 NativeBackend 下发，系统调用仍在执行后端中。读取/控制使用精确且唯一 AUMID；测试再带 expected_title，避免会话已经换歌后还操作它。指定目标失败就失败，禁止发送全局播放键；按应用的音量请求也不能冒充全局音量调整。

`open_song` 只是受限投递：纯数字 ID、读取协议注册中的 cloudmusic.exe、独立 argv、无 shell。不复用整段注册命令，不改注册表；返回 requested 与 playback_confirmed=false，不把进程投递成功当作播放成功。该验证入口没有作为默认 NetEase 播放后端或结果卡自动播放按钮上线。

## 4. Stop 的真实回执揭示了第二种假成功

实机中，客户端 can_stop=false，但 TryStopAsync 仍可能返回 true；随后状态继续 Playing。单凭调用返回值声称“已停止”会再次误导用户。

修复采用两层检查：先检查 Stop 能力，不支持则拒绝，不改成 Pause；对 play/pause/stop，命令接受后短时回读 PlaybackStatus，未确认目标状态就返回错误。最终日志显示 Stop 明确失败，随后独立的 Pause 确认 Paused。用户听感也确认暂停后没有声音。

这种回读只证明客户端报告了对应状态，不证明任意曲目 ID、完整歌曲时长或播放到尾。SMTC 多次 position=0，不能据此画假的播放进度。未来若启用官方后端，UI 应按实际能力显示“暂停”，而不是把暂停暗中包装成真正 Stop。

## 5. Windows 界面验证为什么没有变成正式控制链

官方 CLI 资料中的 orpheus 仅支持 macOS。本机 Windows 协议和显式 webcmd 参数都未完成可重复的数字 ID 定位闭环。UIA 未提供歌曲控件，监督下的 HWND/PID 校验坐标点击只能用于定位试验，不能拿去做长期默认自动点歌。

搜索点击后曾发生曲目变化，用户确认没有手动切歌；当时曲名校验成功拦住后续操作。随后 Monody 的界面/SMTC/听感一致，并完成定向播放、暂停，但客户端精确 song ID 仍未独立读回。保留初轮失败证据，不拿最后一轮声音正常覆盖前面的自动定位问题。

客户端截图只抓目标窗口，含私人界面，收尾删除临时文件，不纳入公开报告。不读取/导出 cookies、密钥或签名流，不修改客户端调试、无障碍或系统协议设置。

## 6. 回归策略与工程取舍

单元测试保护实际风险：缺失权限标志、应用拒绝不是登录过期、不可播原版不变 Remix、队列不擅自选版本、数字 ID 校验、试听不播放、idle 不转控、精确目标不回退全局键、会话歧义拒绝、Stop 不支持/未确认不能报成功。它们覆盖原缺陷，未引入新的大型框架。

前端用真实 API 数据投影到运行中的两角色卡片，再做 DOM 点击与旧 key 操作验证，并明确拦截媒体发送。这层验证针对呈现/路由，不冒充真实 LLM 与原生鼠标端到端。官方客户端音频验证另列，由实机状态与用户听感共同支持。既有拆窗、轮廓、C0 检查保留。

全量 Python 必须从 engine 工作目录运行：现有 BGE 测试使用相对权重路径，从根目录运行会跳过，不能把这种跳过当回归全绿。本轮已按正确目录补跑；最终数字见验收报告。

暂缓的工作包括新的播放器 Runtime、常驻 WinRT 进程、坐标式正式 UI 自动化、官方后端开关。只有支持按 ID 可靠定位、明确所有者/角色失效协议、如实呈现能力之后，才逐步接回现有音乐功能；不因本轮客户端验证扩成大规模重构。
