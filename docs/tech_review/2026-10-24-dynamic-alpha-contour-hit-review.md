# 动态 Alpha 轮廓命中：实现复盘与工程技术说明

日期：2026-10-24  
适用版本：当前 Electron + Vue + Pixi/Live2D 前端实现  
关联验收：[动态轮廓命中 MVP 验收报告](../plan/contour-hit-mvp.md)

## 先说结论

这次效果显著，不是因为把 Electron 窗口改造成了真正的“无窗口原生异形控件”，而是因为把原先的**矩形窗口交互判定**，替换为基于 Live2D 实际渲染结果的**动态 Alpha 轮廓判定**。

也就是说，视觉上的角色在哪里、鼠标认为角色在哪里，第一次使用了同一份像素信息：

```text
Live2D WebGL 实际画面
        │ 每 125ms 读取一次低分辨率 Alpha
        ▼
动态 Alpha 遮罩（192 × 256 左右）
        │
        ├── 鼠标命中 / 点击穿透
        ├── 靠近角色时渐隐
        ├── 拖拽起点判定
        └── 功能岛的模型停留判定
```

透明处不再“看得到桌面却点不到”，身体、衣服等不透明区域仍然可靠接收交互；模型动作、换装或换角色后，遮罩会随渲染画面刷新。它是一个**兼顾现有架构、手感、风险和性能的最小验证**，不是渲染框架替换。

## 原问题：一个透明窗口仍然是矩形窗口

Live2D 画面有透明背景，但 Electron 的浏览器窗口及其点击区域天然是矩形。若以窗口/模型包围盒判定，会产生两个互相矛盾的问题：

1. 允许整个窗口响应鼠标，角色周围的透明区域会挡住桌面、其他应用或截图操作。
2. 直接对整个窗口开启 `setIgnoreMouseEvents(true)`，又会让真实模型、菜单、卡片和拖拽一并失去交互。

早期常见的补救是“鼠标按下后暂时穿透几百毫秒”或仅用一个静态矩形。这类方案不能判断腿间、袖口外侧、发丝周围等透明区域，而且异步切换会带来偶发错点。

本次没有把输入逻辑分散修补，而是先定义一个单一问题：**某个窗口 CSS 坐标是否落在当前角色可交互的可见像素上？** 其余功能都消费这个答案。

## 总体方案：从渲染画布派生一张轻量交互地图

实现位置是 [Live2DCanvas.vue](../../shell/src/renderer/src/components/Live2DCanvas.vue:184)。Pixi 仍负责每帧渲染 Live2D；轮廓采样被挂在 Pixi 的 `UPDATE_PRIORITY.UTILITY` ticker 上，因此在画面已更新后读取，不额外驱动一轮模型渲染。

```text
Pixi / Live2D render canvas (WebGL)
            │
            │ drawImage，缩小到最长边 256px
            ▼
隐藏 2D canvas
            │ getImageData().data 的 A 通道
            ▼
AlphaMask { alpha, width, height, left, top, cssWidth, cssHeight }
            │
            └── alphaHit(mask, x, y, threshold, tolerance)
```

关键控制参数如下：

| 参数 | 当前默认值 | 作用 |
|---|---:|---|
| 采样频率 | 8Hz | 最多约 125ms 更新一次轮廓；避免每帧 GPU/CPU 读回 |
| 遮罩最长边 | 256px | 实测画面约为 192 × 256；足以表现身体与腿间透明区 |
| Alpha 阈值 | 24 / 255 | A 值达到阈值才算角色可点区域 |
| 命中容差 | 2 CSS px | 对轮廓边缘做小范围容错，降低“看起来碰到却点空”的感觉 |

低分辨率不是偷工减料，而是此处最关键的工程取舍。鼠标命中只需要“人体轮廓级别”的答案，不需要重建高清贴图。它把一次读取控制在小型像素阵列，而不是高 DPI 画布的完整分辨率。

## 1. 从真实 Alpha 生成遮罩

### 1.1 采样不依赖模型资源格式

`sampleContour()` 不直接解析 Cubism 模型 JSON、贴图透明度或动作参数，而是从已经完成合成的 WebGL canvas 读取 Alpha。这有三个实际好处：

- Hiyori 和 Hotaru 的模型目录、贴图层数、动作资源不同，但都可直接复用；
- 表情、物理摆动、服装透明材质和模型位移的最终结果由渲染器统一给出；
- 不需要为每个角色人工维护轮廓、多边形或热区数据。

换言之，遮罩是“屏幕上最终看见的像素”的低分辨率快照，而不是对资产作静态猜测。这正是动态轮廓比静态点击区更贴合角色演出的原因。

### 1.2 渐隐不破坏轮廓

角色渐隐是 DOM/CSS 层对容器施加的视觉 opacity；采样源则是 Live2D 的 WebGL canvas。因此即使用户看到角色淡出，源画布内的 Alpha 仍代表模型本身，而不是被 CSS 淡化后的结果。验收中两角色在渐隐时都保有有效遮罩。

这是一个很重要的分层：

```text
模型像素 Alpha：决定“形状”
CSS 渐隐：决定“显示强弱”
输入状态机：决定“此刻是否让模型接管鼠标”
```

如果把这三件事混在一起，渐隐时通常会出现遮罩突然全空、鼠标状态抖动或菜单无法叫回的问题。

### 1.3 换角色时先清空旧遮罩

加载新模型前，`Live2DCanvas.vue` 会清掉当前 `contour`；加载失败、无模型或采样异常时命中函数返回 `false`。因此失败策略是**透明让路**，而非拿上一角色的身体轮廓继续拦截桌面。

这与 Hiyori → Hotaru → Hiyori 的角色隔离原则一致：视觉身份切换过程中，旧角色不应残留在新角色的输入路径中。

## 2. 命中算法：阈值、坐标映射和边缘容差

核心纯函数在 [alphaHit.ts](../../shell/src/renderer/src/utils/alphaHit.ts:3)。它先把鼠标 CSS 坐标映射到缩小后的遮罩坐标，读取对应 A 通道；若中心点透明，再按一个圆形半径探测邻近像素。

```text
中心像素 alpha >= threshold  → 命中
中心透明，但 radius 内有达标像素 → 命中
其他情况                       → 不命中 / 点击穿透
```

容差并不是扩大整个模型包围盒，也不会填满腿之间的大片透明区；它只缓冲轮廓附近少量 CSS 像素。这样可同时保留透明区域穿透和边缘手感。

调试台中的参数是本地响应式偏好，定义在 [useContourPref.ts](../../shell/src/renderer/src/composables/useContourPref.ts)。改动阈值或容差不需要重新加载模型；每次下一次判定直接读取新值。绿色遮罩预览则是同一份采样数据的可视化：绿色代表“超过阈值的基础像素”，不把容差绘制成假轮廓，避免误导调参。

## 3. 最容易被忽略的部分：统一输入仲裁

仅有一张遮罩并不能解决问题。若渐隐、拖拽、菜单、卡片各自独立调用 Electron 的鼠标穿透 API，就会形成最后一次写入者覆盖前者的竞态。

因此 [useMousePassthrough.ts](../../shell/src/renderer/src/composables/useMousePassthrough.ts:1) 成为**唯一**写窗口鼠标穿透状态的地方，并按下列优先级仲裁：

```text
真实 UI（功能岛、面板、结果/选歌卡、聊天输入）  最高优先级：必须可点
             ↓
已捕获的窗口拖拽                               保持交互，直到松开
             ↓
正在渐隐                                     模型本体让出鼠标
             ↓
动态 Alpha 轮廓                              只有身体像素接鼠标
             ↓
透明处                                       交给下层桌面/应用
```

这比“只要鼠标在模型窗口内就阻挡”精细得多，也比每个 composable 各自调用 `setIgnoreMouseEvents` 稳定。

`useFadeOnHover.ts` 现在只产出“是否应该渐隐”的状态，不再直接改鼠标穿透；[usePetDrag.ts](../../shell/src/renderer/src/composables/usePetDrag.ts:20) 和 [useBracketMenu.ts](../../shell/src/renderer/src/composables/useBracketMenu.ts:32) 同样接收同一个 `hitContour`。所有判断由 [App.vue](../../shell/src/renderer/src/App.vue:180) 接线，角色切换期间则强制不认旧轮廓。

## 4. 为什么渐隐与功能岛能一起工作

这两个需求天然容易冲突：角色身体悬停应触发渐隐，但如果渐隐后仍按“模型 hover”立即展开菜单，渐隐会被菜单打开抵消；反过来，若整窗穿透，用户也失去叫回入口。

本次采用两条互补路径：

1. 渐隐开启时，停在角色身体上不会再自动打开菜单，避免反复闪烁；
2. 保留一个始终可交互的右下角 `⋮` 悬浮功能岛入口。命中它时，输入仲裁先认 UI，并主动展开菜单、停止渐隐。

此外，遮罩每次更新后会发送 `yuiro-contour-updated` 事件。即便鼠标静止、模型因动作摆进/摆出鼠标下方，输入层也会重新判定，避免旧“仅靠 mousemove 刷新”造成的状态滞后。

## 5. DPI、缩放和多显示器：坐标必须统一语义

Windows 上 Electron 的窗口 bounds 常以 DIP 表示，网页事件和 Vue 布局使用 CSS px，而真实屏幕还可能有缩放和负坐标显示器。如果直接以 `screenX - windowX` 当画布 x，在非 100% 缩放下会偏移。

[useElectronRelativeMouse.ts](../../shell/src/renderer/src/composables/useElectronRelativeMouse.ts:15) 新增 `relativeCss`：先由原生鼠标位置减去窗口 DIP origin，再按 `CSS 视口尺寸 / DIP 窗口尺寸` 换算成 CSS 坐标。边缘判断也统一改用 CSS 视口尺寸。

这不是为了理论完美，而是轮廓命中能在实际桌面成立的前提。自动化测试刻意覆盖了页面缩放和负坐标的纯函数场景；原生实测未假定 DPR 等于 1，运行环境实报 DPR 约为 1.95。

## 6. 如何验证“真的穿透”，而不是网页里看起来穿透

浏览器的 `dispatchEvent` 只能证明 DOM 事件逻辑，不能证明操作系统是否把鼠标交给了窗口下层。验收脚本 [contour_acceptance.py](../../scripts/diag/contour_acceptance.py:100) 因而创建一个独立的 Win32 下层探针窗口：

```text
最上层：Yuiro always-on-top 角色窗口
中下层：验收脚本自己的 Win32 探针窗口
        ↓ SetCursorPos + mouse_event
探针接收到 WM_LBUTTONDOWN = 真实点击穿透
```

脚本根据宠物真实窗口矩形及网页 CSS 视口比例选择坐标，并对每个角色执行：

- 模型包围盒内的透明点连续点击 5 次；
- 实心身体点连续点击 3 次；
- 渐隐后检查遮罩仍在，并从功能岛入口打开菜单；
- 修改阈值、容差、预览开关，确认跨窗口热更新；
- 记录采样耗时，临时移除/恢复同一 ticker 回调比较 RAF 帧间隔。

最终稳定批次的结果见验收报告：Hiyori/Hotaru 透明点均为 **5/5** 穿透，实心点均为 **0/3** 错误穿透；两者都能在渐隐后由功能岛恢复交互。中途曾在 Vue HMR 更新尚未结束时出现一次不一致计数，该记录明确保留为无效样本，没有被包装成通过结果。

## 7. 性能为什么可接受

性能上的核心避免项有三个：

- **不每帧采样**：8Hz 而非 60Hz；
- **不读全尺寸画布**：最长边 256px；
- **不增加模型渲染**：只在既有渲染后的 utility ticker 上绘制到小型 2D canvas 并读 A 通道。

实测 3 秒窗口中，Hiyori 平均单次采样约 3.82ms，Hotaru 约 4.89ms。1.5 秒短测中，暂停采样到恢复采样的 RAF 帧间隔 P95 分别为 6.7→7.3ms 与 6.7→7.9ms。它说明当前设备、当前两模型下该增量没有显著破坏帧节奏；它不等价于所有 GPU、所有显示器、长期运行下的性能承诺。

尤其应注意 `drawImage(WebGL canvas) + getImageData` 可能触发 GPU→CPU readback。因此现阶段保持“低频、低分辨率、可观测”，而不是贸然把采样升到每帧，才是合理路线。

## 8. 本次真正落地的编码技术

| 技术点 | 具体落点 | 解决的问题 |
|---|---|---|
| WebGL 画布 Alpha 采样 | `Live2DCanvas.vue` | 无须人工角色热区，适配两套不同 Live2D 资源 |
| 低频下采样 | 8Hz / 256px | 在交互精度和 readback 开销间折中 |
| 纯函数命中 | `alphaHit.ts` | 容易单测阈值、洞、容差和空遮罩 |
| 单写入者输入仲裁 | `useMousePassthrough.ts` | 避免渐隐、拖拽、菜单互相抢写穿透状态 |
| 同轮廓复用 | App 注入至 fade/menu/drag | 视觉边界与所有行为边界一致 |
| CSS/DIP 转换 | `relativeCss` | 避免缩放、DPI 时点击坐标漂移 |
| 跨窗口本地热更新 | `useContourPref.ts` + 调试台 | 调阈值不重启、不改角色资源 |
| Win32 下层探针 | `contour_acceptance.py` | 验证操作系统层面的真实穿透 |

## 9. 它不是什么，以及下一步应如何演进

当前 MVP 仍然有一个矩形 Electron HWND；所谓“无窗口感”来自透明画面、局部穿透和小型功能岛，而不是已实现原生无 HWND 或 Windows 逐像素窗口区域。截图软件能否完全不捕捉窗口，也不应据此方案承诺。

已知边界：细发丝、半透明材质、很窄的空隙会受 256px 遮罩与容差影响；模型高速移动时轮廓最多约 125ms 才刷新；尚未覆盖快速扫过后立即点击、多 DPI 跨屏、管理员应用、长时间运行以及所有桌面捕获工具。

推荐后续顺序：

1. 先让用户用 Hiyori、Hotaru 实际体验，按手感而不是猜测微调阈值/容差/采样频率；
2. 补快速点击、跨屏、长时挂载、选歌卡与来源卡焦点的回归；
3. 解决长消息遮挡时，采用“模型展示窗 + 独立气泡/卡片 UI 窗”的屏幕工作区布局。该方案能真正让 UI 移出模型视觉区域，但必须统一 DPI、焦点、角色身份和关闭时序；
4. 只有当上述验证显示 WebGL 读回确实成为瓶颈，才评估原生逐像素 hit-test / 原生渲染承载。不要因为“效果很好”而过早进行高风险框架迁移。

这次最值得保留的不是某个具体阈值，而是工程边界：**渲染产出轮廓事实，输入层集中裁决，其他交互功能只复用这份事实。** 这会让后续角色资产扩展、UI 拆窗和演出交互保持可控。
