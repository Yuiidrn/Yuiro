# Fish HTTP音频分块与音频时钟排期

问题是原Fish适配器等待整句HTTP body完成，首个网络字节即使早到，也不能提前播放。此次在既有Speech管线内局部适配，未替换Runtime或改Agent架构。

`engine/yuiro/audio/wav_stream.py`逐步读取RIFF/fmt/data，限定单声道PCM16，接受流式占位长度、跳过附加块并处理奇数字节对齐。按480ms重新封装独立WAV；尾部不补零，截断报错。`fish.py`的synthesize_stream保持一次请求和原音色参数，逐块生成RMS；aclosing与async with保证提前退出、取消、错误均释放响应。原整句合成保留。

`TTSTaskManager`从每句一个结果变为每句deque加完成标记。消费首块时合成可继续；只有当前句完成并播空缓冲才推进下一句。前一句慢时后句可以合成但不能越序。已交付前缀后错误不重新朗读整句。文字回复也通过同一provider流生成器下发，冻结原session/generation并逐块检查。

`useVoiceInput.ts`在队列内串行解码，提前创建BufferSource，按AudioContext时钟连接排期；不再每480ms等待onended后解码。mouth根据实际活跃子块的时间定位，未来块不提前上报started。stopPlayback用epoch拒绝迟到解码，停止全部当前/未来source，释放占用回执及等待者。旧非流式provider继续原播放方式。文字朗读仍沿用原session/generation护栏，不应误称已具备语音WS的四字段播放租约。

验证包括983项后端测试、类型和构建、生产组件调度专项，以及双角色真实Electron/WebAudio的静音fixture。三次真实HTTP首段855.9–1580.9ms，同请求比完整下载早约1秒。但整合实机又遇Fish首段6795.9ms、完整16768.4ms，块间隔长于音频时长，说明“能够流式”与“稳定连续”是两个要求，后者仍待进一步处理。完整证据与未通过范围见[计划](../plan/tts-first-sentence-latency.md)。

后续技术债：网络欠载可观测性、启动/重新缓冲策略、真实端到端多样本与声学口型验收、文字朗读占用统一、整条音频WS事件代际审计。没有为降低指标偷偷改low模式或音色，也未引入缺少生命周期关闭的常驻HTTP client。

本轮末已补欠载可观测性：同一回合下一块实际排期比上一块结束晚30ms以上时，输出`[voice]`日志及`tts:playback_underrun`的gap_ms；新回合/取消清零，不把跨回合静默当欠载。确定性测试验证中途断供820ms可见，最新类型/构建通过并已加载；它只测音频图空隙，不代表声卡实际声学测量，也尚未自动重新缓冲。

复用缩略图诊断模块时发现其导入即执行main，意外重跑了外观预览验收（8页通过、角色配置前后一致）；已加入口守卫避免后续导入副作用。最终读回Hotaru、idle、麦克风关闭和最新构建。最新构建的长回复滚轮也复验通过，全文结束标记可见，滚动条隐藏。

## 断供缓冲增量

后续已实现有限重新缓冲：只在播空而上游尚未结束时等待后续960–1920ms音频，单次上限1500ms；EOF立即释放尾块，stop清理等待。首块直接播放不引入等待。每次Fish请求生成stream_id，在两个下发通道传递，使新句第一块绕过上一句的欠载策略，不改变原先句序。取消仍用同一个epoch，不另建播放器。mouth在等待时归零，presence的buffering映射为thinking，真正source开始才speaking。

新增生产组件测试覆盖阈值、尾块、超时、取消和新句边界；真实Electron双角色隔离夹具六场景证明无迟到续播、零口型、连续成组排期，未声称正式模型切换/人耳听感通过。最新真实Hotaru短句6块排期连续，5个相邻间隔均0ms；此样本没有断供，不能用它代替重新缓冲场景。最新全量983项、前端类型/构建通过，详见计划的原始证据链接。

诊断复盘：CDP接收时刻含采样延迟，不能等价于音频时刻；改用AudioBufferSource.start的音频图排期比较。Runtime.enable会重放旧console，现建立请求前屏障并清空历史，防止上个夹具的欠载污染本次结果。语音首段、HTTP完成、调试器收到首帧、音频图排期和人耳首音必须分别表述；当前仍没有声学首音P95。
