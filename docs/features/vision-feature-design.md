# 桌宠视觉功能引入与低延迟优化策略：调研、设计与可行性分析

> 状态：设计提案（未实施）。目标里程碑建议：M3+（依赖 M2 记忆与对话链路稳定）。
> 关联文档：`ARCHITECTURE.md`（模块契约）、`docs/agent-memory-context-research.md`、`docs/memory-system.md`。
> 硬件前提：RTX 3060（12GB），已占用：CosyVoice2 TTS ~4.8GB（独立进程）+ ASR/BGE-M3 波动占用——**视觉显存预算必须在此约束下规划**。

---

## 一、前沿项目与产品调研

### 1.1 通用多模态理解（VLM）

| 项目/产品 | 能力 | 对桌宠的参考点 |
|---|---|---|
| GPT-4o / Claude（computer use） | 截屏理解 + 动作决策 | 屏幕理解交互的完整范式；Claude computer use 证明"截屏→结构化描述→决策"链路可行 |
| Gemini 2.x Flash | 低延迟视觉 + 长视频流理解 | **流式视频输入**的产品化；token 成本敏感场景的云端方案 |
| Qwen2.5-VL（3B/7B/72B） | 开源 VLM，OCR 强，支持视觉 agent | **本地部署首选**：3B 版可在 3060 上量化跑；OCR 能力对"看屏幕"场景直接可用 |
| MiniCPM-V 2.6+ | 2~8B 高效 VLM，宣称同尺寸最强 | **本地低延迟首选**：小显存占用，视频帧流式理解支持 |
| OmniParser（Microsoft） | 屏幕 UI 元素解析（icon/文本框检测） | "看屏幕"的结构化中间层：先解析 UI 元素再描述，比整图 VLM 便宜且准 |

### 1.2 桌面感知与陪伴类

| 项目/产品 | 做法 | 参考点 |
|---|---|---|
| Windows Copilot Vision | 截屏 + 云端 VLM，**显式用户授权**、按需开启 | 隐私交互范本：视觉必须 opt-in、有清晰的状态指示 |
| AI/ML 桌宠社区（如 VPet、Bongo Cat 衍生） | 前景窗口检测、时钟/日程驱动行为 | "无 VLM 的伪视觉"：很多陪伴效果靠**窗口标题、前台应用名**这类零成本信号即可实现 |
| 情感计算（表情识别：FER 系列、OpenFace） | 摄像头表情 → 情绪标签 | 摄像头路线的可行组件；成熟轻量（CPU 可跑）但隐私敏感度最高 |
| Anthropic computer use / Open Interpreter | 截屏→理解→（可选）操作 | 屏幕理解与系统操作的分层：理解在 engine/shell，操作必须走 system-daemon（架构红线） |

### 1.3 关键结论

1. "视觉"不是一个功能而是**一组差异化场景**，成本/隐私/延迟差异极大，必须分层设计。
2. **大量陪伴价值可以不经 VLM 获得**：前台应用名、窗口标题、剪贴板、系统事件（这些是 Electron 主进程零成本可得的"轻视觉"信号）。
3. 真正需要 VLM 的场景要过两个闸门：**用户显式授权** + **事件驱动截屏**（绝不常驻轮询）。

## 二、视觉功能分层设计（按成本与风险递增）

### L0：轻视觉——系统信号（零额外模型，强烈建议最先做）

| 信号 | 获取方式（shell 侧 Electron） | 陪伴行为示例 |
|---|---|---|
| 前台应用名/窗口标题 | 主进程轮询/钩子（低频 1–2s） | "写代码写两小时了，歇会儿眼睛" |
| 屏幕 UTF 状态（锁屏/全屏） | 系统 API | 全屏时自动进入安静模式，不打扰 |
| 时间/日程 | 本地 | 上下文注入（夜间、工作日模式切换语气） |
| 剪贴板（可选，显式授权） | 主进程 | 用户复制报错时主动询问"要帮忙看看吗" |

- **架构归属**：信号采集在 shell 主进程，经 WS 事件通道（`events.ts` 扩展）发给 engine，engine 注入对话上下文或触发主动行为。
- **红线合规**：采集的是本机状态，不涉及屏幕内容截图；system-daemon 不参与。

### L1：屏幕理解——事件驱动截屏 + VLM（核心场景）

**触发方式（事件驱动，绝不固定频率轮询）**：

1. 用户主动："帮我看看这个页面/这张图"（拖图进对话 / 快捷键截屏）——**v1 只做这个**。
2. L0 信号触发：检测到前台切到指定应用（如报错弹窗、特定软件）+ 用户事先配置的规则 → 询问式触发（桌宠先问"要我看看吗"，不擅自截屏）。

**链路设计**：

```
触发 ─▶ shell desktopCapturer 截屏（PNG/JPEG）
      ─▶ （可选前置）本地 OCR/规则过滤：画面变化小则直接复用上次描述
      ─▶ engine：VLM 生成结构化场景描述
      ─▶ 注入 AgentLoop 上下文（"当前屏幕：…"）→ LLM 生成回复
```

**模型选型**：

| 方案 | 显存 | 延迟 | 适用 |
|---|---|---|---|
| 本地 Qwen2.5-VL-3B（AWQ/GPTQ 量化） | ~3GB | 0.5–2s/图 | 默认方案，OCR 强 |
| 本地 MiniCPM-V（2B 级） | ~2GB | <1s/图 | 极致低延迟备选 |
| 云端（SiliconFlow/Gemini Flash 等） | 0 | 1–3s（含网络） | 隐私可接受时的高质量备选；复用 SiliconFlow provider 模式 |

### L2：用户视觉——摄像头表情感知（谨慎推进）

- 组件成熟（轻量 FER 模型 CPU 可跑），但**隐私敏感度最高**：必须独立开关、专属指示灯态、明确"不上传不存储原始画面"承诺。
- 产出仅为情绪标签（开心/疲惫/专注…）+ 置信度，作为记忆系统的情绪输入（与日记功能的 `mood_tags` 语义对齐）。
- **结论：v2+ 再评估；先由日记/对话侧情绪分析替代**。

### L3：视觉动作反馈（live2d 眼神跟随等）

- Live2D 层已有渲染管线；视线跟随鼠标、看向屏幕方向等属于**渲染参数调整**，无模型成本，可在交互打磨期顺手做，与 VLM 视觉无关但同属"视觉感"体验。

## 三、低延迟优化策略（视觉链路专项）

### 3.1 原则：两阶段 + 事件驱动 + 缓存

1. **事件驱动截屏**：只在"用户主动/规则触发 + 画面显著变化"时截屏。画面变化检测用感知哈希（pHash）或像素差分（CPU 微秒级），变化小于阈值直接返回缓存描述。**这是最大的延迟杠杆——大部分时刻根本不推理**。
2. **快慢两阶段**：快速层（OCR/模板/上次缓存/小模型）先给出粗描述；只有用户追问或粗描述置信度不足时，才升级到完整 VLM 精分析。对应 Manus 教训：让"便宜的第一步"过滤掉多数场景。
3. **区域裁剪**：截屏后先做显著性/ROI 裁剪（如只取变化区域或中心区域），减少 VLM 输入 token——视觉 token 是延迟大头。
4. **流式输出**：VLM 描述走流式，首 token 出现即注入对话/显示"看到了…"，与聊天链路的流式体验对齐。
5. **KV-cache 友好**：VLM system prompt 固定（借鉴 Manus append-only 原则）；多轮看屏时历史帧描述以文本复用，不重复编码图像。

### 3.2 显存预算（3060 12GB 红线管理）

```
CosyVoice2 TTS   ~4.8GB（独立进程，架构红线，不动）
ASR(faster-whisper) ~1–2GB（按需加载）
BGE-M3            ~1–2GB（记忆嵌入，子进程）
剩余可用          ~3–4GB
```

- **结论：本地 VLM 只能选 ≤3B 量化模型（~2–3GB），且与 TTS 存在竞争**。缓解：
  a. VLM 按需加载/卸载（服务化进程 + 空闲自动释放，与 TTS 同款进程隔离模式——**沿用"TTS 推理不进主进程"红线，视觉推理同样独立进程**）；
  b. 或默认云端 VLM、本地 VLM 作为可选配置（config.toml `[vision].provider`，与 TTS provider 模式一致）。
- 加载预热策略：首次触发前提前加载（用户开启功能时），冷启动等待与 TTS 冷启动经验一致——"先等加载完成再可用"。

### 3.3 链路日志与可观测

遵循「链路日志分阶段定位」红线：`vlog("vision", ...)` 打点——截屏触发原因、前处理耗时、VLM 首 token 耗时、总耗时、缓存命中与否。无此打点，「看屏幕慢」将无从定位（同聊天链路的历史教训）。

## 四、可行性总评与分期路线

### 4.1 可行性矩阵

| 功能层 | 技术可行 | 显存可行 | 隐私风险 | 延迟达标 | 建议 |
|---|---|---|---|---|---|
| L0 轻视觉信号 | 高（Electron 原生） | 零 | 低 | 零推理 | **v1 立即做** |
| L1 用户主动发图/截屏问答 | 高 | 云端=零 / 本地 2–3GB | 中（用户显式发起） | 1–3s 可接受 | **v1（云端）/ v1.5（本地）** |
| L1 规则触发看屏幕 | 中 | 同上 | 中高（需 opt-in+确认交互） | 同上 | v2 |
| L2 摄像头情绪感知 | 高（组件成熟） | 零（CPU） | **高** | <100ms | v2+ 评估 |
| L3 live2d 视线跟随 | 高 | 零 | 无 | 实时 | 随交互打磨插入 |

### 4.2 分期建议

- **v1**：L0 全套（轻视觉信号注入对话上下文）+ 用户主动发图/截屏问答（默认云端 provider，复用 SiliconFlow HTTP 模式；本地 Qwen2.5-VL-3B 作为可选实验配置）。
- **v1.5**：本地 VLM 独立进程服务化 + pHash 事件驱动 + ROI 裁剪 + 流式描述。
- **v2**：规则触发的主动看屏（桌宠询问式）、摄像头情绪感知评估、与日记/记忆系统的情绪信号融合。

### 4.3 风险清单

| 风险 | 缓解 |
|---|---|
| 本地 VLM 与 TTS 抢显存导致 OOM | 进程隔离 + provider 二选一 + 加载前显存检查（沿用 `_configure_cuda_runtime` 同类思路） |
| 视觉功能被用户视为"窥屏" | 一切主动看屏必须 opt-in + 每次触发有可见状态指示（借鉴 Copilot Vision），默认关闭 |
| 截屏内容误入记忆造成隐私污染 | 截屏描述默认不写记忆；如需记忆须复用日记功能的显式授权模式 |
| 云端 provider 截屏上传的合规性 | UI 明示上传行为；提供"仅本地模式"总开关 |

## 六、认得人：身份识别层（追加）

> 上文的 L2"用户视觉"讲的是**表情**（心情如何）；本节讲的是**身份**（**这是谁**）。
> 两者技术同源（摄像头 + 模型），但**隐私等级与产品含义完全不同**：
> 认出"你现在心情不好"是感知；认出"**你是 Yui**"是**认证**。

### 6.1 为什么"认得我"是这一层的真需求

需求原话：**"最重要的是我自己"**。这句话给了明确的价值排序：

- **认出本人** → 一切个性化（语气、称呼、共享记忆的尺度、能开什么玩笑）**才有根**；
- **认出熟人** → 在本人授权的前提下，才谈得上"换个说法打招呼"；
- **认不出 / 陌生人** → **必须退回最保守的行为**（见 6.4）。

**★ 关键：不要把"认出人"做成"播报"。**
`检测到人脸 → 播报"你好 Yui"` 是机械的，且**在多人场景下是社死行为**。
正确做法是：**身份只作为上下文注入**，由她在语气与边界上自然体现 ——
这与"情绪只进 prompt、不进台词"是同一种设计哲学（见 `emotion.style_hint`）。

### 6.2 技术栈（CPU 可跑，不占 TTS 显存）

| 环节 | 方案 | 说明 |
|---|---|---|
| 人脸检测 | **RetinaFace / SCRFD**（轻量） | 帧率不需高（秒级一次足够） |
| 特征提取 | **ArcFace / AdaFace** → 512 维向量 | 业界标准；CPU 单张数十 ms |
| 比对 | 余弦相似度 + 阈值 | **阈值偏严**：宁可认不出，不要认错 |
| 活体检测 | 眨眼 / 微动（可选） | **v2+ 再评估**（照片攻击收益有限） |

**★ 全程不联网、不存照片**：只存**特征向量**（512 维浮点）——
向量不可逆还原成图像，这是"能认人"与"不存生物影像"之间的**最小代价折中**。

### 6.3 三类身份与行为差异

| 身份 | 存储 | 行为 |
|---|---|---|
| **本人** | 一个向量 + `is_owner` 标记 | 完整个性化：共享记忆、称"你"、可以毒舌 |
| **熟人**（本人授权登记） | 每人一个向量 + 称呼 | 礼貌但**有所保留**；**不主动提 Yui 的私事** |
| **陌生人** | 不存储 | 标准礼貌；**不暴露"我认识这台机器的主人"** |

**★ 最后一条是隐私红线**：桌宠不该成为"谁在家 / 谁在用这台电脑"的信息泄露渠道。

### 6.4 有人在场的降级（最容易被忽略的一节）

- **检测到陌生面孔** → **不主动打招呼、不提名字、不念共享记忆**；
- 若此时本人说话 → 正常应答，但注入一条**边界提示**（"当前可能有他人在场"），
  **由她自己在措辞上收敛** —— 而不是弹"检测到陌生人"的框（那同样尴尬）；
- **★ 不做**：不截图留存、不上报、不统计"陌生人出现过几次"。

### 6.5 与"多模态聊天"的分工

两者常被并提，但是两条独立链路：

| | 多模态聊天 | 身份识别 |
|---|---|---|
| 输入 | **用户主动给的图**（拖入 / 截图） | **摄像头**（持续，低频采样） |
| 触发 | 显式（用户动作） | 隐式（人脸出现） |
| 数据 | 图像内容 | **仅特征向量** |
| 失败代价 | 答得不好 | **认错人 / 泄露隐私** |
| 优先级 | **v1** | **v1.5（需 opt-in）** |

**共同点**：都必须**默认关闭 + 清晰状态指示 + 一键关闭**（沿用 L1 的 opt-in 原则）。

### 6.6 分期

- **v1.5**：摄像头身份识别（本地 CPU）+ 三类身份行为差异 + opt-in 与状态指示；
- **v2**：熟人登记流程（本人授权、可随时移除）、与 `Character.affinity_state` 联动
  （**"认得"是关系的一部分**）、他人在场的措辞收敛策略；
- **v2+**：活体检测评估（等出现"照片骗过"的真实案例再说）。

## 七、前端 UI 与反馈（增补）

> 依 `ui-and-integration-guidelines.md`。视觉类功能的 UI **不是呈现能力，而是呈现边界**
> —— 隐私指示器比任何视觉特效都重要。

### 7.1 ★ 隐私指示器（本层最高优先级的 UI）

| 要求 | 实现 |
|---|---|
| **启用即可见** | 摄像头/截屏被启用时，桌宠窗口**常驻**一个小指示（镜头/眼睛图标），**任何时刻可见，不可被隐藏** |
| **一键关闭** | 指示器本身可点 → 立即关闭采集（且立即停模型推理，不只是停止上传） |
| **opt-in 授权** | 首次开启需明确授权对话框（说明：本地处理、不存照片、只存特征向量） |
| **状态可辨** | 采集/暂停/出错三态用颜色区分（如绿/灰/红），避免"看着开着其实挂了" |

**红线**：指示器不能藏在设置里。用户**随时**要能一眼知道"它在看吗"。

### 7.2 不播报（§6 的 UI 推论）

| 事件 | ❌ 错误 UI | ✅ 正确做法 |
|---|---|---|
| 认出本人 | 气泡"你好 Yui！" | **无 UI**，仅注入上下文，语气/称呼自然变化 |
| 检测到陌生人 | 弹框"检测到陌生人" | **无 UI**，仅注入边界提示（§6.4），她自己收敛措辞 |
| 表情识别 | 显示"检测到：开心" | **无 UI**，进 `emotion`（`style_hint`） |

**判断**：视觉的产物是**背景**，背景一旦变成界面元素，就从"感知"退化成"监视"。

### 7.3 用户主动视觉（多模态聊天的 UI）

- 入口：拖图进聊天坞 / 快捷键截屏（**只有用户显式动作才截图**）；
- **截屏瞬间要有明确反馈**（快门感：边框闪一下 + 缩略图进聊天坞）——
  让用户确信"我刚刚给了它什么"；
- 随附图/截图**可见、可删**（发送前可取消）；发送后进 history 的是**描述而非图像**（隐私与体积）。

### 7.4 引擎集成点

- 采集在 **shell 主进程**（§二 L0/L1 已定），经事件通道（`vision:capture` / `attachment:add`，
  `events.ts` 已有类型）送引擎；**system-daemon 不参与**（架构红线）；
- 身份/表情结果分别进 `emotion` 与**上下文注入**（不进台词）；
- 身份库（本人/熟人向量）管理在调试台：登记、命名、**可随时移除**（移除即删除向量）；
- 摄像头/模型未就绪 → 复用 `pipeline:state` 式的**状态事件**，前端显示"不可用"而非静默失败。

### 7.5 Checklist 要点

入口=用户动作（拖图/快捷键/授权后自动）；进行中=采集状态指示（非转圈）；
成功=自然回应（非播报）；失败=状态指示变红 + 说人话；中断=点指示器即停；
**背景 vs 台词=严格只进 prompt**；开关=**默认关闭**、一键关闭；
