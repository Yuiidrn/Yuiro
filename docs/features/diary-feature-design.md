# 桌宠日记功能：设计与可行性分析

> 状态：设计提案（未实施）。目标里程碑建议：M2+。
> 关联文档：`docs/memory-system.md`（记忆系统）、`docs/agent-memory-context-research.md`（业界参照）。
> 核心诉求：**给用户一个记录生活的出口，同时让桌宠"记得你的生活"，增加生活性与陪伴性——但隐私边界由用户完全掌控。**

---

## 一、功能定位与动机

### 1.1 是什么

用户可随时进入"日记模式"，通过**打字或语音持续输入简短内容**（碎片式、多轮追加，长短叙事均可），确认完毕后由桌宠后台 LLM 分析解构并润色，反馈到 UI 供用户编辑审阅；确认后用户可选择：

1. **是否持久化保存**（存为日记文档）
2. **是否写入桌宠记忆**（决定桌宠能否"记住"这段生活）

三档隐私语义：

| 选项 | 效果 | 类比 |
|---|---|---|
| 仅保存，不进记忆 | 日记存在，但检索永远搜不到它 | 用户私密文档 |
| 保存 + 进记忆 | 桌宠可在后续对话中自然提及、关心此事 | "分享给桌宠" |
| 不保存不进记忆 | 阅后即焚 | 类 ChatGPT Temporary Chat |

### 1.2 为什么值得做（业界依据）

- **ChatGPT 记忆调研结论**（见 `agent-memory-context-research.md` §2.1）：96% 的记忆条目由系统主动创建而非用户显式要求——用户其实**欢迎被记住，但要知情可控**。日记功能把"要不要记住"的决定权显式交给用户，是记忆治理的最佳交互形态。
- **陪伴型产品的核心差异化价值**：单轮对话缺乏跨时间的生活连续感。日记提供了**周期性、主动性的陪伴触点**（"你上周说准备的比赛怎么样了？"），这是纯聊天记忆很难自然做到的。
- **生成式智能体（Generative Agents）的反思路线**：短日记是天然的"记忆流"原料，按周/月聚合反思可产出"本月你主要在忙 X、情绪整体偏 Y"的高层画像——比逐句对话记录更干净、更适合进长期记忆。

### 1.3 与现有记忆系统的关系

日记**不是新的记忆层**，而是一个**受控的记忆上游**：

```
日记输入 ──LLM 解构润色──▶ 用户确认 ──(用户选择)──▶ MemorySystem.remember()
                                                    │
                                    与现有 remember() 的区别：
                                    - 显式来源标记 metadata.source = "diary"
                                    - 用户显式授权，而非自动写入
```

## 二、交互流程设计

### 2.1 状态机

```
[正常对话态] ──用户点"写日记"/口头说"我想记一笔"──▶ [日记模式]
                                                      │
                            ┌─────────────────────────┘
                            ▼
                      [持续输入态]  ← 打字逐条追加 / 语音（ASR 实时转写追加）
                            │  （无轮次上限，每次输入独立成段）
                            ▼  用户点"写好了" / 语音说"记完了" / 静默 30s 提示确认
                      [LLM 解构态]  （后台，UI 显示"正在整理…"）
                            │
                            ▼
                      [审阅编辑态]  ← 原始输入与润色稿并列展示（diff 视图）
                            │    可改写、可拒绝润色、可补充
                            │    （循环：再编辑 → 再优化，次数不限）
                            ▼  用户点"确认"
                      [处置选择态]  ← 三选一（见 1.1）
                            │
                ┌───────────┼───────────┐
                ▼           ▼           ▼
          [仅保存]     [保存+进记忆]  [丢弃]
                └───────────┴───────────┘
                            ▼
                      [日记模式退出] → 桌宠口头简短回应（TTS）+ 可选主动追问
```

> **增量（见 §八）**：持续输入态可选**吐槽模式**（随时开关、默认关）；
> 确认录入后新增**总评**环节（收尾仪式）。

### 2.2 持续输入的细节约定

- **语音链路**：复用现有 faster-whisper ASR；日记模式下 ASR 结果**直接追加到草稿区**，界面实时显示转写文本，可手改。

**★ 为什么"不走 AgentLoop"是必要设计（非偏好）** —— 原表述"不打扰、零幻觉回复"太含糊，
真实的硬理由有四条：

| # | 理由 | 证据 / 后果 |
|---|---|---|
| ① | **误触发工具（最硬）** | 预路由对"裸名词命中应用名白名单（记事本/微信/Excel/浏览器/网易云…）"是**确定性触发 `app_open`，完全不经 LLM**。日记里写"今天用记事本记了点东西"→ **真的会把记事本打开**；更糟的是一旦 `tool_ran`，本轮还会顺带写入记忆，**绕过 §3.2 的显式授权** |
| ② | **语义错位** | 日记内容不是"对桌宠说的话"，每段都生成对话回复是错的（回复应由吐槽模式按门控提供，§8.1） |
| ③ | **上下文与 history 污染** | 注入 persona/记忆/history 对"记录生活"无益；且日记原文会进多轮 history，被后续对话带上 |
| ④ | **延迟** | 完整链路含记忆检索（最长 5s 超时）+ 组装 + 可能的工具轮，远慢于"ASR → 草稿区" |

**两条必须澄清的误读**：

- **不走 AgentLoop ≠ 不用 LLM**：解构/润色（§2.3）、吐槽（§8.1）、总评（§8.2）都要 LLM，
  只是走**独立一次性调用** —— **共享 `provider` / persona / trace，不共享对话循环**；
- **"防自动写记忆"不是理由（修正）**：`memory_writer` 仅在 `tool_ran` 时被调用，纯文本轮不写 L2。
  真正保护隐私的是 §3.2 的显式授权协议；此处的实际风险是①引起的**间接写入**。

- **控制意图（缺口，必须补）**：不做完整解析，但"退出日记""删掉刚才那句""看看我上周写的"
  这类**控制指令**不能被当成正文 → 需要**极简控制意图识别**（关键词/小分类即可），
  未被识别的一律**视为正文**（宁可漏判控制，也不误判正文）。
- **打字链路**：草稿区多段列表，每段独立，LLM 解构时以"时间连续的多段生活片段"呈现给模型，不做提前合并。
- **长短叙事分层**：单次日记预期 50–500 字；若用户一次输入超长（>2000 字），UI 提示可拆分，避免 LLM 单次解构质量下降。

### 2.3 LLM 解构润色（非改写）

Prompt 目标是**辅助而非篡改**，输出结构化结果：

```json
{
  "polished_text": "润色稿：修正错别字、理顺语序、保留原意与口语感",
  "summary": "一句话摘要（供记忆注入用，≤50字）",
  "mood_tags": ["疲惫", "期待"],
  "topics": ["毕设", "跑步"],
  "entities": [{"type": "person", "name": "导师"}],
  "followup_question": "桌宠下次可以自然问起的事，如'比赛准备得怎么样了？'",
  "long_term_hint": "short | long   // 短期事件 or 长期叙事（持续状态）"
}
```

要点：

- **润色稿必须逐句对应原文**，禁止虚构补充事实；用户在 diff 视图可一眼识别。
- `followup_question` 是陪伴性的关键产出：进记忆时随 L3 事实一并存储，供桌宠在后续对话中**自然地**发起关心（也解决"跨会话记忆注入了但模型不知道怎么用"的问题）。
- `long_term_hint` 区分长短叙事：短期事件进 L2 情景；长期叙事（如"这学期在准备考研"）进 L3 事实并可参与周/月反思聚合。

## 三、数据模型与持久化设计

### 3.1 新表 `diaries`（SQLite，与记忆库同库或独立库均可，建议独立 `yuiro_diary.db` 以便用户整库导出/删除）

```sql
CREATE TABLE diaries (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  created_at TEXT NOT NULL,            -- ISO8601
  updated_at TEXT NOT NULL,
  raw_text TEXT NOT NULL,              -- 原始输入（多段以 \n\n 分隔）
  polished_text TEXT,                  -- 确认后的定稿（可能等于 raw_text）
  summary TEXT,                        -- 一句话摘要
  mood_tags TEXT,                      -- JSON array
  topics TEXT,                         -- JSON array
  entities TEXT,                       -- JSON array
  followup_question TEXT,
  narrative_type TEXT,                 -- 'short' | 'long'
  privacy TEXT NOT NULL,               -- 'discard' | 'local_only' | 'shared'
  memory_written INTEGER NOT NULL DEFAULT 0,  -- 是否已写入记忆
  source_meta TEXT                     -- 保留扩展字段
);
```

> **结构化升级与回顾入口（见 §九）**：`diary_tags`（可索引标签投影）+ `diary_fts`
> （全文检索）+ 时间线索引；以及调试台/桌宠侧两条回顾入口与隐私档变更联动。

### 3.2 与记忆系统的写入协议

- `privacy = 'shared'` 时：`summary`（+ `followup_question`、`mood_tags`）按 `long_term_hint` 写入 L2 或 L3，`metadata.source = 'diary'`、`metadata.diary_id` 回链。
- `privacy = 'local_only'` 时：**绝不触碰记忆库**；`Retriever.retrieve` 天然搜不到（无需加过滤逻辑——不写入即不可见，符合最小权限）。
- `privacy = 'discard'`：不落库，仅日志留痕（不记内容）。

### 3.3 检索时的呈现约束

带 `source = 'diary'` 的记忆条目注入时，格式上标注"（来自 TA 的日记）"——借鉴 Claude Code「记忆是便签」哲学：让模型知道信息来源与可谈论的边界，避免桌宠说出"我偷看了你的日记"式的出戏内容。

## 四、工程可行性分析

### 4.1 复用度评估（结论：低成本）

| 依赖能力 | 现状 | 复用方式 |
|---|---|---|
| 语音转写 | faster-whisper ASR 已通 | 日记模式直接消费 ASR 流 |
| LLM 流式调用 | `OpenAIProvider.stream_text` 已通 | 解构润色一次非流式调用即可（几百字，延迟 1–3s 可接受） |
| 记忆写入 | `MemorySystem.remember()` 已通 | 新增 `source` metadata 透传 |
| 前端 UI | Electron+Vue3，DevApp 已有面板先例 | 新增 DiaryPanel 组件 |
| TTS 回应 | 各 provider 已通 | 确认后一句简短回应 |

### 4.2 延迟预算

- ASR 转写：实时流式，无额外延迟。
- LLM 解构：非流式 1–3s，且发生**在用户主动确认之后**——等待感被"我写完了，帮我整理"的心理预期吸收，比聊天链路的延迟容忍度高一个量级。
- 总体无端到端红线风险；不需流式优化。

### 4.3 红线合规

- 日记内容不经过 system-daemon、不触发任何 OS 操作——纯 engine 内链路，无沙箱问题。
- 显存无新增压力（ASR/LLM 均复用既有实例）。
- 数据本地存储（SQLite），无云端依赖；若未来接云端 LLM 解构，隐私选项需在 UI 明示"该内容将发送至云端模型"——**建议 v1 固定用本地/现有 provider 并如实标注**。

### 4.4 风险与开放问题

| 风险 | 缓解 |
|---|---|
| LLM 润色"改写过度"或虚构 | diff 视图 + prompt 强约束逐句对应 + 用户可一键拒绝润色 |
| 用户误选"进记忆"后反悔 | 需要反向操作：MemoryManager 面板支持按 `diary_id` 删除对应记忆条目（该面板已存在，加一个入口即可） |
| 桌宠主动追问"过度关心"造成不适 | followup 的使用频率需节流（如同一 followup 只主动提起一次）；这是行为策略问题，留到实现时用 `memory_prompt` 约束 |
| 日记聚合反思（周/月总结）范围蔓延 | 列为 v2，v1 只做单篇解构；反思聚合借鉴 Generative Agents 的定期反思，单独排期 |

- **v1（M2 可排期）**：打字日记 + LLM 润色审阅 + 三档隐私处置 + 写入记忆（含 source 标记）+ MemoryManager 反向删除。

## 六、画像复描：日记最深的用途（追加）

> 上文把日记定位为"**受控的记忆上游**"—— 这是对的，但只用到了它一半的价值。
> 日记真正不可替代的地方在于：**它是用户的自述，而不是对话的副产品。**

### 6.1 为什么"加深画像"不等于"多抽几条 facts"

现有 L3 `FactsStore` 是**离散断言**（`subject / key / value / confidence / decay`），
如 `口味: 不吃辣`、`作息: 熬夜党`。它精确、可查询、可衰减 —— 但它回答的是
"**关于 TA 我知道哪些点**"，而不是"**TA 是个什么样的人**"。

这不是"多与少"，而是**抽象层级**不同：

| | facts（已有） | 画像叙事 profile（本方案新增） |
|---|---|---|
| 形态 | 离散 key/value | 一段连贯描述 |
| 来源 | 对话中零散提及 | **日记自述**（信噪比高得多） |
| 用途 | 精确检索 / 判断 | **理解与共情**的背景 |
| 更新 | 增量 upsert | **定期复描**（重写整段） |

**关键判断**：给模型注入 20 条 facts ≠ 让它"理解这个人"。它需要一段**有因果、
有重心**的描述 —— 而 facts 恰恰**丢掉了因果**：日记里"最近在准备比赛所以睡得晚"
到 facts 层会变成两条互不相干的断言（`在准备比赛` / `作息: 熬夜`），
**因果没了，"理解"也就没了**。

### 6.2 复描机制：逐层抽象

```
原始日记（用户自述，逐篇）
      │  单篇解构（v1 设计：summary / mood_tags / topics / entities）
      ▼
单篇摘要 + 情绪/主题标签（结构化，可直接进记忆）
      │  定期聚合（周 / 月）
      ▼
画像叙事 profile —— "TA 是什么样的人"
      （近期重心 / 情绪基线 / 在意的事 / 变化趋势）
      │  交叉验证
      ▼
facts（已有，精确断言；画像只产出**候选**，仍走 S40 的"两次确认"门槛）
```

**★ 为什么画像不直接反写 facts**：画像出错误伤更大（一句话概括一个人，错了就是
刻板印象），所以画像是**给模型看的背景**，facts 才是**可断言的事实**。画像可以
**提议** facts 候选，但必须走既有的 `_needs_confirmation` 门槛（同一事实说两次
才算稳定）—— **这条 S40 护栏不能因为"来自日记"就放松**。

### 6.3 新增注入通道：`【关于 TA】`

按 S47 的上下文分层（**稳定前缀 + 变化后缀**），画像**一周才复描一次**，
比 facts 还稳定，因此天然该进**缓存前缀区**：

```
① 稳定前缀区（可缓存）
   system → persona → relationship → 【关于 TA 的长程画像】← 新增
   → explicit / facts
② 变化后缀区
   knowledge → task → pending → state → history → user
```

顺带好处：**它还会提升前缀缓存命中率** —— 这正是把 feature 设计与
ContextEngine 语义放在一起考虑的价值。

### 6.4 必须有的三个"可控"

画像比 facts 更需要透明度 —— 因为它是**系统的推断**，而 facts 至少有用户原话。

| 要求 | 做法 | 理由 |
|---|---|---|
| **可见** | 调试台/前端可查看当前画像全文 | 用户有权知道自己被怎样理解 |
| **可溯源** | 每条断言回指 `diary_id` / 时间范围 | 否则无法回答"它凭什么这么说我" |
| **可纠正** | 可编辑 / 删除 / 标记"这条不对" | **删掉后下次复描要避开** |

**★ 第三条最容易漏**：若用户删掉一条画像、下次复描又从同样日记推出来，
**用户会觉得"它根本不听我的"**。因此需要一张 `profile_exclusions`（被否定的断言），
复描时作为**负样本**注入 —— 这与"记忆可删除"是同一件事的两面。

### 6.5 分期

- **v1（与日记 v1 同批）**：单篇解构 + `profile_candidates` 落库（**先不注入**）；
- **v1.5**：**周复描** + `【关于 TA】` 注入通道 + 调试台画像查看/编辑；
- **v2**：月复描 + 排除表（否定反馈闭环）+ 与 `RelationshipMemory` 里程碑交叉印证。

## 七、前端 UI 与反馈（增补）

> 依 `ui-and-integration-guidelines.md`。§6.4 的"可见/可溯源/可纠正"**本质上是 UI 需求**
> —— 没有界面，三者都落不了地。

### 7.1 四态反馈

| 态 | 设计 |
|---|---|
| **进行中** | 解构/复描是**后台任务**，不阻塞对话。提示要**汇总而非逐篇**：批量整理时一次活动提示"正在整理今天的日记…"，完成后撤下。**避免每篇都弹**（会变成骚扰） |
| **成功** | 气泡一句**自然的话**（"今天这篇我记下了"），**不报技术细节**（"已写入 L2/L3 并生成 3 条 facts"是反例） |
| **失败** | **绝不丢原文**：解构失败只影响结构化，原文照存；提示"这篇没整理好，稍后再试"，并给重试入口 |
| **空闲** | 提醒/进度都撤下 |

### 7.2 入口与提醒（克制优先）

> **★ 入口形态已修订（2026-09，用户实测反馈）**：原写"不新造独立窗口"，
> 但 §2.2 的硬边界是"日记输入**不走 AgentLoop**"（正文里的"记事本/微信"会被
> 预路由当指令真的去开应用）。内嵌在聊天坞里，这条边界**用户看不见** ——
> 用户会以为自己是在"跟她说话"。故改为：
>
> | 入口 | 形态 |
> |---|---|
> | **唯一入口** | 悬浮功能岛「日记」按钮（右列中间，取代原「日志」）→ **独立编辑窗口** |
>
> 聊天坞里的日记按钮与内嵌面板**已下掉**（用户实测反馈：日记塞进输入胶囊上方
> 只会挤占对话空间）—— 日记只有这一个窗口，草稿权威仍在引擎侧 `DiarySession`。
>
> **交互策略也已修订**：原设计"持续输入态完全沉默"以保护心流，用户明确否掉 ——
> 「日记不需要考虑什么心流，就是要让桌宠尽可能地多交互」。现在**每写一段（含语音
> 识别结果）都会同时作为聊天输入交给她接话**（开关默认开，可关成"纯记录"）。
> 存储仍走独立 `diary:*` 通道（正文里的应用名不会触发工具操作），
> 但"让她接话"这一步是**真正的对话**（走桌宠自己的 session，回复落在桌宠窗口）。
> 停笔吐槽（`diary:quip`）不再被前端请求 —— 每段都真接话，再来一路吐槽只会重复。

- 提醒：**一天最多一次**，且受免打扰开关约束（夜间/全屏/专注时不弹）；
- 提醒文案是**邀请**不是通知："今天想写点什么吗？"（可忽略，不追问）。

### 7.3 ★ 画像的三可控 → 落到具体界面

| 要求 | UI 实现 | 位置 |
|---|---|---|
| **可见** | 画像全文面板（近期重心/情绪基线/在意的事/变化趋势） | 调试台新增"画像"页签 |
| **可溯源** | 每条断言可展开看**来源日记**（日期 + 原文片段） | 同上，点击断言展开 |
| **可纠正** | 编辑 / 删除 / 标记"这条不对"（写 `profile_exclusions`） | 同上；**纠正后下次复描必须避开** |

**关键交互**：用户标记"不对"时，反馈要**明确承认**（"好，这条我不再用了"）——
若无反馈，用户无法确认纠正是否生效，会重复纠正（§6.4 已指出这是最容易漏的一环）。

### 7.4 引擎集成点

- 解构/复描走**任务系统**（`task_*`？不适合）→ 建议用**后台任务 + 事件**（对齐现有 `_spawn` 模式），
  事件进 `agent.activity`，**Trace 加阶段**（`diary_deconstruct` / `profile_redraw`）；
- 画像注入走 `ContextEngine.build` 的参数（**稳定前缀区**，§6.3），
  **不允许**在 AgentLoop 侧 append（S47 已修过的旁路 bug）；
- `profile_exclusions` 随画像一起进 `build`，作为**负样本**；
- 写操作（删除/纠正画像）走**审批门风格**的确认（不可逆）。

### 7.5 Checklist 要点

入口=聊天坞/每日一次邀请；进行中=汇总式活动提示；成功=自然语句 + 可查面板；
失败=保留原文 + 重试；中断=可取消整理；**背景 vs 台词=默认只进 prompt**（不主动念日记）；
开关=提醒可关、自动整理可关；偏好项=提醒时间/是否自动解构/面板可见性；免打扰=提醒收敛；
可见性=§7.3。

## 八、加装设计：吐槽模式与总评（增补）

> 需求原话：**"持续输入的过程中可以开关'吐槽模式'；确认录入后再来个总评"**。
> 本章是对 §2.1 状态机与 §2.2 输入约定的**增量**，不改动既有链路语义。

### 8.0 它们各自填补什么空白

| 现状 | 空缺 | 加装 |
|---|---|---|
| §2.2 持续输入态**完全沉默**（刻意不走 AgentLoop：避免误触发工具与语义错位，见 §2.2） | 用户写日记时桌宠像记事本，**陪伴感为零** | **吐槽模式**：可选、低强度、随时可关的伴随轨道 |
| §2.1 退出时只有"一句简短回应（TTS）" | 刚刚写完一整篇，收尾太轻，**缺少"被读过"的感觉** | **总评**：确认录入后的收尾仪式 |

**★ 两者共同的设计矛盾**：日记是**心流活动**，任何实时反馈都可能打断思路。
因此这两个功能的成功标准**不是"说得多"，而是"在该说的时候说得准，且随时能闭嘴"**。
吐槽默认**关**、总评可**关**，不是保守，而是正确。

---

### 8.1 吐槽模式（持续输入期的伴随轨道）

#### 8.1.1 它是什么

用户在**持续输入态**下，桌宠偶尔对刚写的内容来一句**极短**的反应（≤15 字，带梗但不抢戏）。
**它不是对话**：不产生轮次、不写记忆、不进 history、不触发工具、不需要用户回复。

#### 8.1.2 ★ 触发门控（本设计最关键的部分）

吐槽的失败模式只有一个：**说太多**。所以触发条件必须**同时**满足：

| 门控 | 规则 | 理由 |
|---|---|---|
| **停顿触发** | 用户停笔 ≥ 3s（有"喘息窗口"）才可发声 | 持续快速输入 = 心流中 → **闭嘴优先** |
| **段落边界** | 优先在用户主动分段/回车处吐槽 | 段落是天然的意义边界 |
| **频率上限** | 每分钟 ≤1 次；同一段不重复 | 避免变成弹幕 |
| **长度上限** | ≤15 字，一句话 | 短才不会打断思路 |
| **内容筛选** | 只挑少数"有反应价值"的句子（自嘲、反差、明显的情绪） | 平铺直叙的句子不值得打断 |
| **情绪安全阀** | 见 8.1.4 —— **负面情绪时自动降级或闭嘴** | 在用户难过时吐槽是产品灾难 |

#### 8.1.3 开关语义

| 项 | 设计 |
|---|---|
| 默认 | **关闭**（心流优先；符合规约"不打扰"原则） |
| 位置 | 日记模式输入区的**一个可见小开关**（不是藏在设置里 —— 用户要能一眼切） |
| 随时可切 | 输入过程中可随时开/关；**关闭后在途吐槽立即作废**（走 generation/取消，旧结果不得回流） |
| 状态可见 | 开启时有一个**轻量常驻指示**（如草稿区角标），不做动画、不闪烁 |
| 免打扰联动 | 免打扰/专注态下**自动静默**（开关保持，但不发声） |

#### 8.1.4 ★ 情绪安全阀（红线）

吐槽是基于人设（她可能是毒舌型）的，但**人设不能高于用户的情绪状态**：

| 日记情绪 | 吐槽行为 |
|---|---|
| 正面 / 平静 | 允许俏皮、小吐槽 |
| 低落 / 焦虑 / 崩溃 | **自动降级为温柔共情**，或**直接闭嘴**（宁可沉默，绝不冒犯） |
| 无法判断 | **按保守处理**（不出声） |

**实现要点**：不能等 LLM 解构（那在确认之后）——实时判定要用**轻量信号**：
关键词/短句情绪分类即可（复用 `emotion_engine` 的既有思路），**宁可误判为负面而沉默**。

**★ 禁令**：不评价日记的"好坏"、不说教、不建议"你应该…"。日记是**倾诉**，不是交付物。

#### 8.1.5 呈现与架构归属

| 项 | 决策 | 理由 |
|---|---|---|
| 呈现 | **气泡（`showSpeech`）**，不遮挡草稿区 | 轻量、可忽略 |
| 出声 | **默认静音，不进 TTS** | 写日记时有声音会打断思路；TTS 由偏好项单独开 |
| 链路 | **独立轻量链路**，**不走 AgentLoop** | 同 §2.2 的四条理由（首要：预路由白名单会真的执行 `app_open`）；**共享 provider，不共享对话循环** |
| prompt 组装 | 独立轻量 prompt（persona + 当前片段 + 情绪约束） | **不是**主对话上下文 → 不写记忆、不进 `_history`、不参与主组装 |
| 观测 | Trace 打点 `diary_quip`（触发/被门控/取消） | 节流参数要靠它调，否则只能靠感觉 |
| 落库 | **不落库**（吐槽无长期价值，落库还会污染） | 仅日志留痕，不记内容 |

> **架构说明（避免误读规约）**：`ui-and-integration-guidelines.md` §四 要求"上下文走
> ContextEngine 唯一入口"——那是针对**主对话上下文**。吐槽是**旁路的人格化输出**，
> 既不写记忆也不进 history，因此**不构成"多路径组装"**；但它**必须复用 persona**
> 以保证人设一致（不能另写一套人设文案）。
>
> 同理，它与解构/润色共用 **LLM `provider` 与 trace**，但**不共用对话循环/上下文组装** ——
> "共享底层能力、不共享对话语义"是这条链路的总原则。

### 8.2 总评（确认录入后的收尾）

#### 8.2.1 时机与定位

```
[处置选择态]（保存 / 保存+进记忆 / 丢弃）
        ▼  用户点"确认"
[★ 总评态]  ← 新增：她读完这一篇后的整体感受（2–4 句）
        ▼
[日记模式退出]
```

- **在"确认"之后**（处置与隐私选择已完成），与用户选哪档隐私**无关** —— 总评是对这一篇的
  感受，不是对"是否记住"的回应；
- **一次性**：不重复生成、不因刷新重复播报；
- **总评 ≠ 摘要**：摘要（`summary`）是解构给**记忆系统**用的；总评是给**用户**听的
  —— 一个面向系统，一个面向人。

#### 8.2.2 内容结构（质量红线）

| 组成 | 要求 |
|---|---|
| 情感回应 | 先回应情绪（不是先点评内容） |
| **一个具体观察** | **必须能指回日记里的具体细节** —— 这是总评与"可替换套话"的分界线（见下） |
| 轻轻的期待/约定 | 与 `followup_question` 呼应，但**不在当下追问**（追问属于后续对话，此处只埋线） |
| 长度 | 2–4 句 |

**★ 质量红线**：总评里每一句都必须**锚定日记的具体内容**。
若把总评原封不动发给另一篇日记也成立，那就是**失败的总评**（套话）。
这与 §6.2 的"因果不能丢"是同一条要求。

**语气同样受情绪安全阀约束**（8.1.4）：负面日记 → 共情优先，**禁止说教与正能量说教式收尾**。

#### 8.2.3 UI 与可控

| 项 | 设计 |
|---|---|
| 进行中 | 复用 §7.1 的活动提示："正在读你写的…"（**不要**做成进度条） |
| 呈现 | 气泡 + **可选出声**（收尾仪式适合 TTS，与吐槽默认静音正好相反） |
| 跳过 | 用户可随时"不用说了"（**不是所有人都愿意被评价**，尤其私密内容） |
| 开关 | 偏好项"总评"可关；关闭后回到既有的一句简短回应 |
| 回看 | 存 `diaries.closing_review`，日记详情可回看（**不重复播报**） |
| 失败降级 | 生成失败 → **不阻塞流程**，退回既有的一句简短回应（绝不弹错误） |
| 归属 | 总评是**她的话**，不是用户的事实 → **不进 L2/L3**；可作为 v1.5 复描的输入之一 |

#### 8.2.4 与画像复描（§六）的关系

总评是"她的感受"，画像是"系统的推断" —— 两者**层级不同、不可混用**：

- 总评**不直接进 facts**（它是人设化输出，不是断言）；
- 但"我注意到你最近常提到 X"这类跨篇观察，正是 §6.2 复描的**雏形** →
  归入 v1.5 的画像通道，且**必须过 S40 两次确认门槛**。

### 8.4 风险与红线（本章新增）

| 风险 | 缓解 |
|---|---|
| **吐槽打断心流（最致命）** | 8.1.2 全套门控 + **默认关** + "心流优先沉默" |
| **在用户难过时吐槽** | 8.1.4 情绪安全阀 + 无法判断时沉默 |
| **总评变成套话/鸡汤** | 8.2.2 质量红线：每句必须锚定具体内容；**禁止说教** |
| 总评变"评分"（这篇日记打几分） | **明确禁止**：不给评价、不给建议，只给回应 |
| ★ **隐私错位（重要）** | 三档隐私（§1.1）是**存储**语义，而吐槽/总评是**处理**语义 —— 它们需要把内容交给 LLM。若 provider 在云端，**即使选"仅保存不进记忆"，内容仍会外发**。→ 必须在 UI 明示"吐槽/总评需要模型处理"；提供"用本地模型才开这两个功能"的说明，或允许单独关闭 |
| 深夜/免打扰时段被打扰 | 免打扰自动静默（8.1.3） |

### 8.7 输出链路归属：文字共享出口，语音共享通道（增补）

| 层 | 与主对话共用？ | 说明 |
|---|---|---|
| **文字气泡** | ✅ **同一个 `showSpeech` 出口** | 它本就是通用出口（`chat:assistant` / `llm:text` / `proactive:*` 都在用）。吐槽/总评复用它 → 视觉一致、阅读时长估算与自动淡出一致 |
| **事件类型** | ❌ **新增** `diary:quip` / `diary:review` | 不复用 `chat:assistant`（那是 AgentLoop 的产物、被前端当对话回复处理）。前端用**同一个气泡组件**渲染新事件 —— **同一出口，不同信使** |
| **语音 TTS** | ✅ **必须共用同一 session 通道** | TTS 按 `session_id` 单通道（`_tts_managers[sid]` / `_speaking[sid]` / `interrupt(sid)` / epoch 作废） |
| **对话语义** | ❌ 不共享 | 不写 history、不写记忆、不触发工具（§8.1.5） |

**为什么 TTS 必须共享（分通道会坏三件事）**：

1. 与主对话音频**同时播放**（两个音频源打架）；
2. **barge-in 切不断它** —— 用户开口时总评还在念（打断语义失效）；
3. ★ **`_asr_locked` 失效 → 自激循环**：TTS 播放期间锁 ASR 是防"她把自己的声音听成用户输入"；
   若另开通道，这个锁不覆盖，她会**听自己说话并回应自己**。

**两个必须处理的冲突**：

1. **TTS 通道互斥** → 日记输出必须**串行化**（对齐既有做法：`media:play` 直连走同一个
   `chat_queue`，"保证与聊天回合互斥，不会两边抢播放器"）；建议日记模式的输出同样经**同一串行协调**。
2. **气泡与活动提示联动**：`showSpeech` 会 `clearActivity()`（回复到达即收起"进行中"）——
   若吐槽在总评生成期间插入，会把"正在读你写的…"清掉 → 状态错乱。
   建议：日记模式下活动提示**独立于对话的 activity 槽位**，或吐槽时不清 activity。

**一句话结论**：**共享"出口与通道"（UI 一致、可打断、不自激），不共享"对话语义"（不进 history/记忆/工具）。**

## 九、落库日记的结构化存储与回顾入口（增补）

> 需求原话：**"落库的日记需要有结构化保存以及 UI 入口进行回顾"**。
> **如果不做这一章，日记功能就只有"写"没有"看"** —— 存了却翻不到，等于没存。

### 9.0 分层前提：日记库 ≠ 记忆库

| | 记忆库（`yuiro_memory.db`） | 日记库（`yuiro_diary.db`） |
|---|---|---|
| 服务对象 | **她记得**（语义检索、注入上下文） | **用户回顾**（浏览、筛选、检索、导出） |
| 检索方式 | 向量 + FTS + RRF | **FTS5 全文 + 结构化标签**（无需向量） |
| 写入门槛 | 用户显式授权（§3.2） | 用户确认保存 |
| 删除语义 | 删了就"她不记得" | 删了是**用户销毁自己的记录** |

**结论**：回顾**不依赖记忆库**。两库通过 `diary_id` **双向回链**（§9.1.3），但检索各走各的
—— 这样"仅保存不进记忆"的日记依然可被用户回顾（否则该档位就变成了"阅后即焚"，语义就错了）。

### 9.1 结构化保存（schema 升级）

#### 9.1.1 为什么不能只靠 `diaries` 表的 JSON 字段

§3.1 的 `mood_tags / topics / entities` 是 **JSON 存 TEXT** —— 写入方便，但**回顾场景下不可用**：
筛选（"看我这个月焦虑的日子"）、统计（情绪趋势）、复描输入（§六）都需要**可索引**的结构。

#### 9.1.2 表结构增量

```sql
-- ① 标签关联表（把 JSON 摊平成可索引结构；一篇文章对多条标签）
CREATE TABLE diary_tags (
  diary_id   INTEGER NOT NULL REFERENCES diaries(id) ON DELETE CASCADE,
  tag_type   TEXT NOT NULL,      -- 'mood' | 'topic' | 'entity'
  tag_value  TEXT NOT NULL,
  PRIMARY KEY (diary_id, tag_type, tag_value)
);
CREATE INDEX idx_diary_tags_lookup ON diary_tags(tag_type, tag_value);

-- ② 全文检索（复用 memory/store.py 的 FTS5 trigram 经验）
CREATE VIRTUAL TABLE diary_fts USING fts5(
  raw_text, polished_text, summary, closing_review,
  content='diaries', content_rowid='id', tokenize='trigram'
);

-- ③ 时间线索引（按时间倒序浏览是最主要的访问模式）
CREATE INDEX idx_diaries_created ON diaries(created_at DESC);

-- ④ 结构化升级：日记库自带 schema 版本，便于后续迁移
PRAGMA user_version = 1;
```

**约定**：`diaries.*_tags` 的 JSON 列**保留**（作为原始产物，便于回放/溯源），
`diary_tags` 是它的**投影**；写入时同事务双写，保证不漂移。

#### 9.1.3 与记忆库的双向回链

| 方向 | 载体 | 回答什么问题 |
|---|---|---|
| 日记 → 记忆 | `Memory.meta["diary_id"]`（已定，§3.2） | "这篇日记进记忆了吗、进了哪条" |
| **记忆 → 日记** | 反查 `diary_id` | **"她怎么知道这件事的？"** → 点开来源日记 |

**为什么必须双向**：只有正向时，用户看到她说起某事却**无法追溯来源**，
信任就断了（与 §6.4"可溯源"同一条要求：**推断必须可回溯**）。

#### 9.1.4 ★ 隐私档的可变更（一致性红线）

用户在回顾界面**改档位**时，必须**同时修正记忆库**，否则就是"谎报隐私"：

| 变更 | 必须做的事 |
|---|---|
| 保存+进记忆 → **仅保存** | **删除已写入的记忆条目**（按 `diary_id` 反查后删，并清向量/FTS，S50 的四表齐删教训） |
| 仅保存 → 保存+进记忆 | 按 §3.2 协议**补写**（此时才首次写入） |
| 任意 → 阅后即焚 | 删日记 + 删对应记忆（**双重销毁，需强确认**） |

**这条最容易漏**：用户以为"改成私密就安全了"，而记忆里还留着 —— 之前 S50 排查的
"清了但还在"是同一类病（**用户可见的操作与实际存储状态必须一致**）。

### 9.2 回顾入口（双入口，各有分工）

#### 9.2.1 桌宠侧：自然语言 + 结果卡（她能帮你翻）

- 触发："我上周写的日记呢""我最近写了什么""上次那篇关于比赛的"；
- 走**工具**：`diary_recall(query?, date_from?, date_to?, mood?, topic?, limit=5)`；
- 返回**结果卡**（复用 S45/§7.2 机制）：日期 + 摘要 + 情绪标签，**点开看详情**；
- **她不朗读内容**（除非用户明确说"念给我听"）—— 回顾是**浏览**，不是播报（规约"不打扰"）。

#### 9.2.2 调试台"日记"页签：完整回顾（用户的主场）

| 区块 | 内容 |
|---|---|
| **时间线** | 按月分组、倒序；每条显示日期 / 摘要 / 情绪标签 / **隐私档徽标** |
| **筛选** | 情绪、主题、时间范围、隐私档（"只看没进记忆的"） |
| **搜索** | FTS 全文（正文/摘要/总评） |
| **统计** | 情绪趋势（按月）、写了多少篇、连续天数（**只呈现事实，不做评价**） |
| **批量操作** | 导出（Markdown / JSON）、批量改隐私档、删除 |

#### 9.2.3 详情视图

定稿 ↔ 原文 diff（§2.3 已定）**+ 总评（§8.2）+ 标签 + 记忆写入状态 + 来源回链**，
并提供：改隐私档（§9.1.4 的联动）、编辑、删除、**"她怎么知道的"**（展开看是哪些记忆条目来自本篇）。

#### 9.2.4 ★ 隐私语义在回顾中的正确处理（最易设计错）

`local_only`（仅保存）的语义是**"她检索不到"**，**不是"用户不能看"** —— 用户看自己的东西是天经地义的：

| 场景 | `shared` | `local_only` | `discard` |
|---|---|---|---|
| 调试台回顾/搜索 | ✅ 全文 | ✅ **全文**（用户自己的库） | ❌ 不存在（未落库） |
| 桌宠侧 `diary_recall` | ✅ 返回摘要 | ⚠️ **只返回元信息**："9-12 有一篇日记（未共享）" | ❌ 不存在 |
| 进上下文/记忆 | ✅ | ❌ | ❌ |

**实现要点**：回顾界面的读取**不经过 LLM**（直接读库渲染）—— 这既是隐私最优，
也避免了"让模型复述用户私密内容"这一无谓的暴露面。

### 9.3 引擎集成点

| 关注点 | 决策 |
|---|---|
| 工具 | `diary_recall`（`effect = read`，**可安全重放**；`approval_required = False`） |
| 无日记库时 | 工具可正常注册（库总存在），但**空结果显示"还没写过日记"**，不报错 |
| 上下文 | 命中的日记摘要按需进 `tool_results`（变化后缀区，S47），**受隐私档过滤**（§9.2.4） |
| 观测 | Trace：`diary_recall`（query / 命中数 / 耗时） |
| 事件 | 回顾结果为**卡片事件**（非气泡），前端渲染（§7.2 通道） |
| 前台操作 | 改档位/删除走**主进程对话框确认**（不可逆，尤其"阅后即焚"） |

### 9.4 四态反馈

| 态 | 设计 |
|---|---|
| 进行中 | "正在翻你的日记…"（检索可能带全文扫描，需反馈） |
| 成功 | 结果卡；空结果**明确说"没找到"**（不编造"你好像写过…"） |
| 失败 | 说人话（库不可用/查询过长），给下一步（缩短关键词/去掉筛选） |
| 空闲 | 卡片收起 |

**中断**：可打断（`read` 类工具无副作用，打断零代价）。
**开关**：回顾入口本身不需要开关；但存在**"她能否主动提起日记内容"**的独立开关（区别于"用户主动问"）。

### 9.5 分期

- **v1**：`diary_tags` + `diary_fts` + 调试台时间线/筛选/搜索 + 详情视图 + 隐私档变更联动（§9.1.4）；
- **v1.5**：桌宠侧 `diary_recall` 工具 + 结果卡 + 记忆→日记回链展示 + 导出 Markdown；
- **v2**：情绪趋势统计、跨篇观察（与 §6.2 复描打通，走 S40 门槛）。

### 9.6 风险

| 风险 | 缓解 |
|---|---|
| ★ 改档位后记忆未同步（谎报隐私） | §9.1.4 强制联动 + 测试钉住（对齐 S50 的四表齐删） |
| 日记被当"事实"注入并称"你日记里说…" | `source='diary'` 标注（§3.3）+ prompt 边界：**不说"我看了你的日记"** |
| 回顾界面成为隐私泄露面（同桌可见） | 回顾页**默认需要显式打开**；不做桌面常驻窗口；不自动展开全文 |
| FTS 中文检索质量 | 沿用 memory 库的 trigram 方案（已验证），不另起一套 |
| 用户删除后期望"她也忘掉" | §9.1.4：删日记时**提示**是否同时删记忆（默认**同时删**，符合直觉） |

**Checklist（按规约 §三）**：入口=说话/调试台页签；进行中="正在翻你的日记…"；
成功=结果卡（用户可核验）；失败=说人话+下一步；中断=可打断；
**背景 vs 台词=不朗读、不主动评价**；开关=回顾无需开关，但"她主动提日记"独立可控；
偏好项=时间线密度/是否显示情绪标签；免打扰=不主动提；可见性=§9.2.2/§9.2.3。
