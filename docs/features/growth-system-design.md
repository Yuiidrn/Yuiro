# 成长系统：从幼女心智到少女：设计、技术栈与分期

> 状态：**设计提案（未实施）**。目标里程碑：**远期**（M4+）。本文档的存在意义是
> **提前定性 + 定技术栈**，避免真做时被"成长"这个含糊概念拖着走。
> 关联：`docs/spec/architecture-goal.md`（Harness 总纲）、
> `docs/features/diary-feature-design.md`（§六 画像复描是成长的燃料）、
> `docs/llm-finetune-mac-persona.md`（已有的微调先例）。
>
> 核心诉求：**让"她"随着相处而变化 —— 不只是数值变大，而是"认知、语言、
> 声音、对自己的理解"都往前走一程。**

---

## 一、为什么现在的 `Character` 不是"成长"

现状（`engine/yuiro/emotion/__init__.py`）：

```python
@dataclass
class Character:
    affinity: float = 0.0     # 与用户的情感纽带
    xp: int = 0
    level: int = 1
    attributes: dict[str, float] = ...   # intelligence / charisma / agility / stamina
    XP_PER_LEVEL = 100
```

这是**RPG 数值层**，它回答"**我们关系多深**"，但**不回答"她是谁、她变了没有"**：

| | 数值成长（已有） | 认知成长（本方案） |
|---|---|---|
| 表现 | Lv.5 → Lv.6，属性 +0.5 | **她说话的方式、理解的东西变了** |
| 可感知 | 需要看面板才知道 | **对话里就能感到"她长大了"** |
| 载体 | 一个数字 | 语言 / 认知 / **声音** / 自我叙事 |
| 可逆 | 数值可波动 | **成长阶段应当单调不可逆** |

**一句话**：数值成长是**给玩家的反馈**；认知成长是**角色本身的演变**。
本方案做后者，并且**复用前者的数值作为驱动力**（见 §四）。

---

## 二、成长的四个维度

成长不是一个标量。至少这四个维度**必须分别设计**，因为它们的技术栈完全不同：

### 2.1 语言复杂度（最容易做，收益最直接）

| 阶段 | 特征 | 例 |
|---|---|---|
| 幼女 | 短句、叠词、直白、无隐喻 | "不要！我不困……好吧有一点。" |
| 少女 | 长句、能反讽、会用比喻、有分寸 | "行吧——反正你每次说'马上就睡'都是这个语气。" |

**技术**：**提示词演化**（本阶段不需要任何模型训练，见 §六 阶段 A）。

### 2.2 认知能力（抽象层级）

从**具象**到**能理解隐喻、暗示、言外之意**。这与 2.1 相关但不同：
语言是"怎么表达"，认知是"能理解什么"。

**技术**：同样靠提示词 + **few-shot 示例随阶段变化**（示例示范"她如何理解一句话"）。

### 2.3 声线（感知最强，技术风险最低）

| 阶段 | 目标音色 | instruct 示例 |
|---|---|---|
| 幼女 | 稚嫩、偏高、语速略快 | "用稚嫩、清亮的童声说话，语速稍快、尾音上扬。" |
| 少女 | 清亮但稳、有起落 | "用清亮而从容的少女声说话，语速自然、有情绪起落。" |

**★ 技术**：CosyVoice 的 **`instruct` 参数就是天然接口**（现有
`tts.instruct_zh` 已是这一形态）—— **改一行文本就能换一种说话的"年纪"**，
无需重新训练。这是四个维度里**性价比最高**的一环。

### 2.4 自我叙事：她记得的"自己"

**这是最容易被忽略、却最关键的一维。**

现有记忆系统里，`facts` 是**关于用户**的（`facts_subject = "Yui"`）。
成长需要的是**另一份**：**关于她自己的** —— 她过了几个生日、第一次成功做了什么、
你们一起经历过什么。

**★ 为什么必须独立**：如果她没有"自己的过去"，那"成长"只是参数变化，
用户感知到的是"版本更新"而不是"她长大了"。**自我叙事是成长的锚**。

**技术**：新增 `self_facts`（同样的 `FactsStore` 结构，`subject = "Yuiro"`）+
**里程碑事件流**（可复用 `RelationshipMemory` 的里程碑机制）。

## 三、★ 最关键的设计：成长必须是**渐变**，不能是阶跃

这是整个方案里**唯一不可妥协**的一条。

**反例**：某天达到阈值，她的声音突然从童声变成少女声 ——
用户的感受不是"她长大了"，而是"**出 bug 了**"或"**换人了**"。

**机制设计**（三层）：

```
阶段量 stage（连续，0.0 → N.0）
      │  由 §四 的驱动力累积（单调不减）
      ├─ 内部：保持连续，用于插值
      ▼
阈值离散化 → 稳定阶段（幼女 / 少女 / …）—— 用于**选择提示词与 instruct**
      │
      ▼
过渡期（跨阈值前后的一个区间，如 ±10%）
      └─ 提示词**混合**：两个阶段的 persona 同时注入，并显式说明
         "你正处在变化中——有时会不自觉地说得更成熟或更幼稚，这是自然的"
```

**★ 过渡期是"叙事化"的机会**：与其偷偷切换，不如**让成长本身成为可谈论的事**。
她会说"最近好像……说话变得不一样了？"—— 这把一个技术切换变成了**情感事件**。

**另一个必须做的**：**成长可见**。用户应当能查"她现在的阶段 / 还差多少 / 最近的变化"，
否则渐变太慢，用户根本感知不到 —— 那成长就只剩设定文档里的意义。

## 四、驱动来源：什么让她成长

| 来源 | 现状 | 说明 |
|---|---|---|
| 互动次数 | ✅ `_interaction_reward()` 已加 xp | 基础量，**但衰减**（防刷） |
| 关系深度 | ✅ `affinity` | 权重更高（真正亲近才有成长） |
| **共同经历** | 🟡 任务完成 / 日记可复用 | **★ 权重最高**：一起做过的事比闲聊 100 轮更"长记性" |
| **陪伴时长** | ❌ 需要新统计 | 低频、慢，但**最符合"长大"的隐喻** |
| **认知刺激** | ❌ 需要新判定 | 见过新话题 / 新场景（不是重复闲聊） |

**★ 设计原则**：**不要用"说了多少话"当主驱动** —— 那会鼓励刷量，
产生的成长是"数字游戏"而不是"相处"。权重上：**共同经历 > 关系深度 > 陪伴时长 > 互动次数**。

## 五、单调性：成长 vs 情绪（重要区分）

成长系统最容易被情绪系统污染。两者必须**明确分开**：

| | 成长阶段 | 情绪 / 亲密度 |
|---|---|---|
| 方向 | **单调不减**（原则上不倒退） | 可升可降，日常波动 |
| 时间尺度 | 周 / 月 | 分钟 / 小时 |
| 载体 | `stage`（连续量 + 稳定阶段） | `EmotionEngine` / `affinity` |
| 用户感知 | "她变了" | "她今天心情不错" |

**为什么不能混**：如果吵架导致"心智倒退"，那是**人格羞辱**而非成长设计。
负面互动应该影响**情绪与亲和度**，**但不该让"长大"这件事被撤销**。

**唯一例外**：`affinity_state`（stranger → partner）**可以**回退 ——
但那是**关系的状态**，不是**她的成长阶段**。这两者在数据上就该是两个字段。

## 六、技术栈分期（从零成本到重投入）

| 阶段 | 做法 | 需要什么 | 成本 | 建议 |
|---|---|---|---|---|
| **A** | **提示词 + instruct 参数化** | 无（纯配置） | **极低** | **v1 必做** |
| **B** | 提示词 + **few-shot 示例集**随阶段切换 | 撰写示例（人工） | 低 | v1.5 |
| **C** | **LoRA 微调**分阶段小模型 | 训练数据 + 显存 | 中高 | v2 评估 |
| **D** | **多声线**（每阶段一个参考音频 / 声音模型） | CosyVoice 已支持 zero-shot | 中 | v2 |
| **E** | 独立模型 / 独立人格 | —— | 很高 | v3+ |

**★ 为什么 A 就能撑起 v1**：语言复杂度与认知层级**本质上都是提示词问题**。
`_DEFAULT_PERSONA_PROMPT` 已经是"参数化的人格"，把它变成**按 stage 选一份**
就是最小可用版本 —— 而且**完全可逆、可随时调优劣**，是验证"这个方向对不对"的正确起点。

**★ C 的现成基础**：`docs/llm-finetune-mac-persona.md` 已有本项目的人设微调先例，
不是从零开始。

**★ D 的前提**：CosyVoice 的 zero-shot 克隆需要**参考音频**。多声线的现实路径是
**准备 2~3 段不同"年纪感"的参考音频**，而不是训练多个模型。

## 七、与现有系统的接口

```
Character（数值，已有）           ──┐
  xp / level / affinity            │  作为 stage 的**输入信号**
                                   ▼
RelationshipMemory（里程碑）  ──▶ GrowthState ──▶ stage（连续）
TaskRuntime（任务完成）       ──▶   │              │
DiaryFeature（共同经历）      ──▶   │              ├─▶ ContextEngine：选 persona 版本
                                   │              │   （进**稳定前缀区**，低频变化）
陪伴时长统计（新增）          ──▶   │              │
                                   │              └─▶ TTS：选 instruct（换"年纪感"）
                                   ▼
                              self_facts（自我叙事，新 store，复用 FactsStore 结构）
                                   │
                                   └─▶ ContextEngine：【我是谁】段（低频，前缀区）
```

**三个不新增存储的理由**：
1. `stage` 是**纯派生量**（由已有信号算出）→ 只需存"上次结算时间 + 累计量"；
2. `self_facts` 直接**复用 `FactsStore`**（换 `subject`）→ 不造第二套真相源；
3. 里程碑**复用 `RelationshipMemory`** → 已有机制不重写。

> 这与本会话反复坚持的原则一致：**新能力优先用"现有设施 + 一个薄层"实现**。
> 三次"多套并存导致漂移"的教训（提示词三份、上下文注入两条、工具轮绕预算）
> 说明：**每多一套存储，未来就多一处会不同步的地方。**

**与 S47 排序的呼应**：`【我是谁】` 与 persona 一样**变化极慢**，
属于**缓存前缀区** —— 成长系统不会伤害前缀缓存命中率（这是设计时就该考虑的事）。

## 八、分期路线与风险

### 分期

- **v1（远期首个可做版本）**：`GrowthState` + stage 连续量 + **prompt/instruct 参数化**
  （阶段 A）+ 成长可见（可查询当前阶段与进度）+ 过渡期提示词混合；
- **v1.5**：`self_facts` 自我叙事 + few-shot 示例集（阶段 B）+ 与日记/任务完成联动；
- **v2**：LoRA 分阶段微调评估（阶段 C）+ 多参考音频声线（阶段 D）+ 月/季度成长报告。

### 风险

| 风险 | 缓解 |
|---|---|
| **阶跃感**（最致命） | §三 的过渡期混合 + 成长可谈论化；**宁可慢，不可跳** |
| 用户觉得"她变了我不喜欢了" | 阶段**可回档**（允许用户设定 / 锁定阶段）—— 成长是默认路径，不是强制 |
| 成长太慢，用户感知不到 | 成长可见面板 + **里程碑式"会说出口"的变化**（她会自己提起来） |
| 微调数据不足 / 效果不稳定 | 阶段 A/B（提示词路线）**长期可用**，C 是增强而非替代 |
| 与情绪系统混淆 | §五 的字段分离：`stage`（单调）vs `emotion`/`affinity`（波动） |
| 声线与 persona 不匹配（童声说毒舌台词） | instruct 与 persona **同源于 stage**，一起切换，不允许单独调 |

### 开放问题（留待实施时定）

1. **阶段划分几档**？（幼女 / 少女 / …建议**先 2~3 档**，多了难以写好提示词）
2. **成长速度由谁定**？（体验上偏慢更好，但需要用户可调）
3. **她知道自己"在成长"吗**？（建议：**过渡期知道，稳定期不刻意提** —— 否则像报进度条）

## 九、前端 UI 与反馈（增补）

> 依 `ui-and-integration-guidelines.md`。**本文档的 UI 结论与其它功能相反**：
> 别的功能要"看得见"，成长**恰恰要看不见** —— §三 的"渐变不阶跃"在 UI 上的推论是：
> **任何"升级动画/等级条/经验值"都是设计失败**（那正是把渐变变回阶跃）。

### 9.1 核心原则：她"变了"，而不是"她升级了"

| 做法 | 判定 |
|---|---|
| 桌宠本体显示等级/进度条/经验值 | **绝不**（把渐变的认知变化降级成数值） |
| 升级动画、特效、提示音 | **绝不**（阶跃感的最强形式） |
| 台词、语气、称呼、知识边界的**自然变化** | ✅ **这才是成长的呈现** |
| 里程碑时**她自己提起来**（"我们好像认识挺久了"） | ✅ **最高级形式**：反馈即人格 |

### 9.2 "可查"而非"常显"

- 用户想知道"她到什么阶段了"时，有一个**主动可查**的入口（设置/调试台"成长"面板：
  当前阶段、稳定度、驱动来源统计）；
- **默认不展示**：她不会主动报进度（§八 开放问题 3 的结论）；
- 过渡期例外：过渡期**可以说"我最近好像有点不一样"**（有自指才有"成长感"），
  稳定期不刻意提。

### 9.3 可控与回档（风险的 UI 出口）

| 风险（§八） | UI 出口 |
|---|---|
| 用户觉得"她变了我不喜欢了" | **阶段可回档/可锁定**：设置里"回到上一阶段""锁在当前阶段" |
| 成长太快/太慢 | 速度滑块（**热重载**，副作用在下次复描/切换时生效） |
| 声线与人设不匹配 | 阶段切换时**台词与声线必须一起变**（§八 末行），UI 上不允许单独调 |

**回档必须真正生效**：回档后注入的 `stage` 立即变化，且**不留下"她记得自己升级过"的痕迹**
（否则回档变成表演）。

### 9.4 引擎集成点

- `GrowthState` 走 **config/persist**（对齐 `RelationshipMemory` 的轻量 JSON 落盘），
  config schema 暴露给调试台（**热重载**）；
- `stage` 作为 **persona 段的一部分**注入（`ContextEngine.build` 的 persona 参数），
  **进稳定前缀区**（成长一周才变一次，比 facts 更稳定 → 缓存友好）；
- 与 `emotion`（波动）严格分字段（§五），UI 上**永不合并展示**；
- 与日记/任务联动的成长驱动 → 走**事件**，Trace 记录（`growth_advance`），便于回溯"为什么涨了"。

### 9.5 Checklist 要点

入口=用户主动查询/设置面板；进行中=**无**（成长没有"进行中"，它是持续的）；
成功=语言与行为的变化（非界面）；失败=N/A；中断=可锁定/回档；
**背景 vs 台词=默认只进 prompt**；开关=可锁定阶段、可关闭成长；
偏好项=速度/阶段锁定（热重载）；免打扰=成长不产生任何主动提示；可见性=§9.2 面板。
