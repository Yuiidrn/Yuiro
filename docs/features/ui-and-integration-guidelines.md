## 一、UI 设计四条原则

### 原则 1：反馈四态 —— 任何等待都必须有"进行中"

| 态 | 必须给出 | 反例（真实出现过的失败） |
|---|---|---|
| 进行中 | 可感知的活动提示 | 首歌 2–6s 无任何反应 → 用户以为没听见 |
| 成功 | 结果 + 可核验的证据（来源/链接/状态） | "刚帮你弄好了"但实际没执行（媒体撒谎，S49） |
| 失败 | **说人话的原因 + 下一步** | 静默降级（BGE 降级数周无人发现，S50） |
| 空闲 | 明确回到常态 | 活动提示不撤，桌宠一直"忙" |

**铁律**：`进行中` 必须来自**引擎的真实阶段事件**，不是 UI 自己假装的动画。
引擎已有 `/ws/audio` 阶段链（`llm:start → llm:text → tts:start …`）与
`agent.activity` 事件 —— **新功能优先复用它们，而不是新造一套状态**。

### 原则 2：永远可中断

进行中的一切（LLM 生成、TTS 播放、长任务、检索）都要能被 `interrupt` 打断，
且打断后**旧结果不得回流**（generation 机制，见 `runtime-contract.md` §3）。
UI 侧要给出可打断的入口（barge-in 说话 / 点一下 / Esc）。

### 原则 3：不打扰（克制是功能的一部分）

- 免打扰开关必须**对所有新增行为生效**（调试台已有"免打扰"项）；
- **只进 prompt、不进台词**：情绪、身份、成长、在场者等**背景信息**由她自然体现，
  绝不播报（`vision §六` 的"不要做成播报"与 `emotion.style_hint` 同一条哲学）；
- 静默/全屏/用户专注时自动收敛。

### 原则 4：可配置 + 热重载

所有新增 UI 的开关/位置/尺寸走**调试台偏好项**（`use*Pref` composable + localStorage），
**拖滑杆即时生效、没有"应用"按钮**（既有约定）。
新功能至少要有一个"关掉它"的开关。

## 二、可复用的 UI 机制（先查表，再设计）

| 机制 | 位置 | 用它来表达 |
|---|---|---|
| 语音气泡 | `showSpeech` / `clearActivity` | 她的**话**（回复、主动搭话） |
| 活动提示 | `agent.activity` → 活动气泡 | **进行中**（正在打开应用…、正在查…） |
| 结果卡 | `useResultCardPref` + 卡片组件（S45） | **可选择/可核验的结构化结果**（歌曲候选、来源列表） |
| 聊天坞 | `useChatDockPref` | 连续多轮文字交互的**输入与历史** |
| 审批对话框 | `approval:required`（主进程 dialog） | **危险/不可逆动作**的确认（写操作、外部影响） |
| 表情/动作/表演 | `emotion:set` / `avatar:*` | 情绪与行为的**非语言反馈** |
| 调试台面板 | `DevApp.vue` + `configCatalog` | **可见/可纠正**（画像、记忆、检索词、状态自检） |
| 阶段事件链 | `/ws/audio` 的 `pipeline/vad/asr/llm/tts:*` | **链路级进度与故障定位** |

**选择顺序**：能进 prompt 的不进 UI > 能进气泡的不开卡片 > 能进卡片的不弹框 > 弹框只给不可逆动作。

## 三、每个功能必须回答的 UI Checklist

> 直接复制到各文档的"前端 UI 与反馈"一节逐条回答。

1. **入口**：用户怎么触发？（说话 / 点聊天坞 / 拖入 / 快捷键 / 自动）
2. **进行中**：等多久？给出什么反馈？来自哪个引擎事件？
3. **成功**：结果呈现形态（气泡 / 卡片 / 表情）？**用户如何核验**（来源、链接、状态）？
4. **失败**：怎么说人话？给出什么下一步？绝不静默。
5. **中断**：怎么打断？打断后旧结果怎么作废？
6. **背景 vs 台词**：这条信息是"她自然体现"还是"明确说出来"？**默认后者不做**。
7. **开关**：用户怎么关掉它？默认开还是关（隐私类必须默认关）？
8. **偏好项**：有哪些可调（位置/尺寸/透明度/频率）？是否热重载？
9. **免打扰**：在此开关下行为如何收敛？
10. **可见性**：用户能否查看/纠正系统对他的推断（画像、记忆、检索词）？

## 四、引擎集成：必须复用的架构优势

新功能**不允许绕过**下列既有机制另起一套（S47 的教训：多路径并存 → 必然不同步）。

| 架构能力 | 复用方式 | 为什么不能绕 |
|---|---|---|
| 工具层 `BaseTool` | 新能力做成工具（`name/description/schema/execute`） | 自动获得 gating、审批、结果卡、状态摘要 |
| **副作用分级** `effect` | 显式声明 `read` / `local` / `external` | 崩溃恢复（S48）据此判断能否重放 |
| **审批门** `approval_required` | 不可逆/对外影响必须 `True` | 绕过后就失去了唯一的"用户同意"节点 |
| **事件总线** `EventBus` / `/ws/audio` | 阶段事件统一出口 | UI 反馈的真实性依赖它 |
| **ContextEngine**（唯一组装入口） | 新上下文段通过 `build(...)` 参数进入 | 绕过则不受预算约束、不进组装日志（S47 修过的真 bug） |
| **稳定前缀 + 变化后缀** | 长程稳定信息进前缀，每轮变化的进后缀 | 直接决定前缀缓存命中率（延迟） |
| **Generation 作废** | 旧代际结果不得进当前上下文/记忆/TTS | 否则打断后仍会"续上旧话" |
| **Trace 观测** | 新链路补阶段打点（含耗时/数量） | 没有观测的优化都是"感觉快了" |
| **keychain + config schema** | 密钥走 keychain（`key_ref`），开关走 config | 铁律：key 不落盘、不入日志 |
| **记忆写入门槛** | 外部/推断数据默认不入 L2/L3（S40 两次确认） | 防止画像污染（S50 实测过） |

**集成自检**：功能上线后，下列问题应能回答"是" ——
① 工具在 schema 里按 `requires_env` 正确隐藏？
② 危险步进审批门？
③ 上下文出现在组装日志里且计入预算？
④ trace 里能看到它的阶段？
⑤ 打断后旧结果不回流？

## 六、验收标准（engine + UI 双面，缺一不算完成）

| 维度 | 验收 |
|---|---|
| 功能 | 正常路径可用，且有测试钉住（含降级路径） |
| **反馈** | 四态齐全；进行中来自真实事件；失败说人话 |
| **可控** | 有开关；隐私类默认关；偏好项热重载 |
| **可中断** | 打断生效且旧结果作废（有测试） |
| **集成** | §四 自检五项全"是" |
| **可观测** | trace 有阶段；调试台可见关键状态 |
