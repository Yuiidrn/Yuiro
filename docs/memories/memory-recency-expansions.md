## 〇、已落地基础（本节只读，不重复实施）

以下改进已完成并验证（测试 `engine/tests/test_agent_chat_reply.py`，9/9 通过）：

| 项 | 位置 | 作用 |
|---|---|---|
| 阶段② `chat_reply` + `tool_choice=required` | `agent/__init__.py` + `tools/system_tool.py` | 机制性消灭"光说不做"静默失败 |

## 一、改进 4：查询扩展 / 多视角召回（高召回率）

**问题**：单条 query 检索容易漏。例如"下一首"作为检索词，难以召回"打开了网易云音乐在放歌"这类记忆。

**方案 A（轻量，零额外 LLM 调用）**：复用现成的 `_keyword_route`（`agent/__init__.py`）意图判定结果，命中 media/app 时**顺带生成一个补充检索视角**：
- 命中媒体控制 → 额外检索视角 `["媒体控制", "播放状态", "音乐"]`
- 命中 app 打开 → 额外检索视角 `[app_name]`
- 两个视角的检索结果做 RRF 合并去重

**方案 B（强，需一次 LLM 调用）**：对话前用 LLM 把用户短命令扩写成多个语义检索 query（如"下一首"→ ["切歌","媒体控制","网易云"]），再分别检索融合。

> 落地优先级：方案 A > 方案 B。方案 A 复用预路由、零成本；方案 B 效果上限更高但增加延迟与 token 开销。

**改动点**：`agent/__init__.py` 的 `send` 中记忆检索段（当前 `memory_mems = await self._memory.retrieve(text, top_k=3)`），改为按意图生成多 query 后融合。

## 二、改进 5：记忆时效衰减 / 去重（长期丰富不膨胀）

**问题**：记忆库越用越多，旧记忆与最新状态冲突（如"用户用网易云" vs "用户改用 QQ 音乐"），且老记忆与当前无关时仍占注入位。

**方案**：
1. **L3 事实 upsert 已做**（`FactsStore.upsert_fact` 按 subject+key 覆盖）——保持"用户偏好"是最新值，不分裂。
2. **L2 情境时效衰减**：`Retriever.retrieve` 返回的 `Memory.meta` 已含 `ts`。RRF 融合时加衰减因子 `1/(1 + age_days * λ)`，老记忆自然沉底，近期记忆更鲜明——"像人"的长期印象（有持续相关的印象）与短期新鲜（近期更显著）并存。
3. **物理清理（可选）**：超过阈值（如 90 天）且 `salience` 低的情境记忆可定时归档删除，控制库体积。

**改动点**：`Retriever._rrf`（或 `retrieve` 后排序）加入基于 `ts` 的衰减权重；`SQLiteVecStore` 可加一个 `prune_old(threshold)` 方法。

## 三、改进 6：写入侧情绪 / 意图打标（记忆更"像人"）

**问题**：目前 L2 情境只存文本，缺少"当时的情绪/意图"维度，检索和注入时无法区分"用户抱怨"与"用户下命令"。

**方案**：`remember` 写入时给 L2 片段打上结构化标签，存入 `meta`（`store.add_message` 增列或 JSON 字段）：
- `meta["intent"]`：命令/闲聊/提问/情感
- `meta["mood"]`：正面/负面/中性（可用 `_keyword_route` + 简单情绪词典初判）
- 检索时可按意图过滤（"只回忆与当前意图同类的过往"），注入时按情绪上下文适配（闲聊时带上"上次你说不开心"）。

**改动点**：`MemorySystem.remember` 增加标签参数；`store.add_message` 支持附加 meta；`Retriever.retrieve` 支持按意图过滤。

## 四、改进 7：记忆注入的"能力边界"声明（人设稳定补充）

**问题**：分通道后，情境层只在 `episodic_inject=True` 时注入。但**默认关闭情境层**也意味着丢失"过往互动脉络"，闲聊连贯性打折。

**方案**：引入一个**可选的"印象级摘要"层**——定期（或每次对话后）用 LLM 把一段闲聊压缩成一句**中立印象**（如"用户最近工作压力大"），单独存为 `kind="impression"` 的 L3 记忆。该层既保留个性化温情，又不含"我打开过 X"的动作范例，天然不污染工具决策，可作为情境层的安全替代。

**改动点**：`MemorySystem` 增加印象写入方法；`_build_messages` 增加印象通道（`kind="impression"`，并入事实层或独立）。需在 LLM 与延迟成本间权衡（多一次压缩调用）。

---

## 五、改进 8：工具记忆的"状态-命令"双向索引（高召回 + 精准动作）

**问题**：改进 3 已把工具轮写成片段 `[已调用工具: X] 用户说: Y`，但检索仍是"整条文本相似度"。当用户换一种说法（"放首歌" vs "打开网易云"）时，动作索引 `X` 与命令 `Y` 的关联不够结构化。

**方案**：把工具片段拆成**结构化记录**写入独立表（`tool_memories: command | tool_name | args | timestamp`），而非塞进纯文本：
- 检索时先按语义匹配 `command`，再按 `tool_name`/`args` 精确命中动作。
- 注入时渲染成 `"当用户说[command]时，执行了[tool_name(args)]"` 的模板，让 LLM 学到"命令→动作"映射，提升模糊命令的意图识别。

**改动点**：新增 `ToolMemoryStore`（或复用 `SQLiteVecStore` 扩展表）；`AgentLoop` 工具执行成功后结构化写入；检索融合进 `MemorySystem.retrieve`。

## 六、改进 9：召回结果的可解释性 / 调试面（工程可维护性）

**问题**：RRF 融合了向量 + FTS + recency，出问题时难排查"为什么召回这条 / 漏了那条"。

**方案**：
1. 给 `Memory` 增加 `meta["reason"]`：标记该条来自向量命中/FTS 命中/新近度、各自的贡献分数。
2. 增加 `engine/scripts/debug_memory.py` 脚本：给定 query，打印每条候选的分项分数与命中来源，便于调参（`rrf_k`、`top_k`、衰减 λ）。
3. 把 `_keyword_route` 的意图判定结果写入调试日志，与记忆召回联查。

**改动点**：`Retriever.retrieve` 记录分项；新增调试脚本。

## 七、落地优先级建议

| 优先级 | 项 | 理由 |
|---|---|---|
| P0 | 改进 4 方案 A（多视角召回） | 复用预路由、零成本，直接提升召回率 |
| P0 | 改进 5（时效衰减） | 长期记忆不膨胀、不冲突，代价小 |
| P1 | 改进 6（情绪/意图打标） | 记忆更"像人"，为后续按意图过滤打底 |
| P1 | 改进 8（命令-动作索引） | 结构化后模糊命令识别提升，工程价值高 |
| P2 | 改进 7（印象级摘要） | 需 LLM 调用，收益与成本权衡后再定 |
| P2 | 改进 9（可解释性） | 工具性，调参期才刚需 |

> **通用原则**：任何"恢复/增强记忆注入"的改动，都必须以 `tool_choice=required` 兜底 + `episodic_inject`/`history_inject` 开关为安全网，先小范围开启实测工具触发率，再逐步放开。
