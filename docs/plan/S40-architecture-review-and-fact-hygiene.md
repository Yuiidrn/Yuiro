## 1. 架构串联度：**主干通了，接缝系统性薄弱**

### 1.1 证据：最近六个 Sprint 抓到的"断点"全在接缝处

| # | 断点 | 层与层的接缝 | 发现于 |
|---|---|---|---|
| 1 | TaskRuntime 事件**从未发布**（`session_id` 漏传，被 `except` 吞掉） | Task → EventBus | S18 |
| 2 | ACTION 意图**永久压制** EMOTION（只看优先级、不看时效） | Avatar 内部仲裁 ↔ 上游 | S18 |
| 3 | 工具结果**不进下一轮上下文** → 重复调用 → 被去重挡死 | Agent ↔ 上下文组装 | S38 |
| 4 | 工具结果**二次 JSON 转义**（长度翻倍、需解两层） | 后端 ↔ 工具层 | S38 |
| 5 | **没有 `file_list`** —— "整理文件夹"无从起步 | 能力清单 ↔ 场景 | S38 |
| 6 | `file_move` 把"移到新目录"当成"重命名" | 语义 ↔ 执行 | S38 |
| 7 | 调试注记被模型模仿，**被 TTS 念出来** | 记忆/history ↔ 输出 | S34 |
| 8 | TTS 的 trace 打点落到**下一轮**的 trace 上 | 音频 ↔ 观测 | S37 |
| 9 | 工具执行期**界面静默**（"像空壳"） | 执行 ↔ 反馈 | S39 |

**规律**：**几乎没有一个问题是"层内算错"，全都是"谁把什么传给谁"没定义清楚。**
每层单测都过（450+ passed），但**接缝没有测试**。

### 1.2 结构性根因（三处）

| 根因 | 表现 | 代价 |
|---|---|---|
| **事件出口有三个**：`EventBus.publish` / `broadcast_control` / `VoicePipeline._emit_event` | 谁该走哪个没有约定 → 漏发（#1 就是：契约存在、没人调用） | 反馈丢失、跨模块联动不可靠 |
| **上下文注入通道有 8 条**：system / persona / facts / knowledge / relationship / state_notes / pending / history（S38 又加了 `round_tool_results`） | 各自为政，加一条忘一条（#3 就是漏了"工具结果"这条） | "工具做了事但模型看不见" |
| **交互状态只有"单槽"**：`pending` 只存**上一条问询文本** | 需要多步交互的流程（选版本 → 确认 → 播放；扫码 → 等待 → 登录）靠自然语言接续 | **这正是 ncm-cli 个性化操作反馈差的结构性原因** |

### 1.3 关于 ncm-cli：需要你给一个具体例子

从代码看，媒体工具的"个性化操作"（`need_choice` 选版本、扫码登录）依赖：

```
工具返回 need_choice/pending → AgentLoop 登记 pending（单槽）
   → 下一轮把 pending 文本注入 system → 用户答"确认" → 模型重新调工具
```

**脆弱点**：
- pending 是**一个字符串**，没有结构化字段（选项列表、等待类型、超时）；
- 用户答非所问时报废阈值只有 `PENDING_MAX_TURNS`；
- 交互过程中**没有"我现在在等你做 X"的显式状态**（前端也看不到）。

**但我需要你一个具体例子**（哪句话 → 它怎么反应 → 你期望什么）才能精准定位 ——
"反馈不良"可能是：选项没展示全 / 答"确认"它理解错 / 中途再说别的就断片 / 状态不可见。
**这四个的修法完全不同**，猜错就白做。

## 2. history 与 memory：**过重，且有实测数据**

### 2.1 实测（引擎日志里的一轮组装）

```
[context] 组装 36 段 / 估算 2915 tokens（预算 6000）
  system:994  persona:396  relationship:65  facts:121  knowledge:360
  history:6 history:64 history:8 history:72 ... （共 20+ 段，累计 ≈1000）
  user:4
```

| 组成 | tokens | 性质 |
|---|---|---|
| system + persona | **1390** | 固定开销（每轮都带） |
| facts + knowledge + relationship | 546 | 记忆注入（**facts 是全量常驻**） |
| **history** | **≈1000（20+ 段）** | **全量注入最近 40 条消息** |
| user | 4 | — |

**结论：history 占了约 1/3，且是"全量"而非"按需"。**

### 2.2 两个具体的"重"

| 问题 | 现状 | 建议 |
|---|---|---|
| **history 全量注入** | `_history` 最多 40 条消息（≈20 轮），每轮**全部**注入 | 改成**只注入最近 N 轮**（如 6 轮 / 12 条）；更早的交给记忆系统（它本来就该干这个） |
| **facts 全量常驻** | 所有 facts 无条件进 system（"自我认知锚点"） | 加**条数/置信度门槛**（如 top 20 且 confidence ≥ 0.7）—— 否则 100 条画像会吃掉 1300 tokens |

> 这两个改动都**不难**，但会改变"人设稳定性"的手感，**建议你拍板后我再动**。

## 3. 事实记忆：**实测污染 + 已修（四道闸门）**

### 3.1 铁证（直接查记忆库）

```
facts（9 行）：
  ✅ 听歌习惯: 喜欢跳过前奏直接听主歌部分
  ✅ 籍贯: 广东          ✅ 常用音乐应用: 网易云音乐
  ❌ 名字: 什么名字                    ← 用户反问"我的名字是什么名字？"
  ❌ 歌曲偏好: 《谁》Live版             ← 单首歌当成稳定画像
  ⚠️ subject 不统一：多数是 Yui，两条是 用户
```

这些一旦入库就进入「自我认知」**常驻注入**，人设被噪声带偏。

### 3.2 四道闸门（本次实现）

| # | 闸门 | 拦什么 |
|---|---|---|
| 1 | **值过滤** `_is_plausible_fact_value` | 疑问词（"什么名字""哪个"）、**指示代词开头**（"这首歌""刚才那个"= 当下感受）、测试性发言（"试试看""随便"） |
| 2 | **LLM 触发门槛** | 去掉"长度 ≥ 12 就抽"的兜底 —— 只在高信号词命中时才调 LLM（省成本 + 防误记） |
| 3 | **LLM prompt 收紧** | 明确排除：提问/反问、临时感受、测试性发言、一次性请求；**宁可写"无"** |
| 4 | **二次确认** `_gate_facts` | 弱信号事实（我是/我喜欢/我讨厌…）**同一 key+value 出现 2 次才入库**；声明式事实（名字/住址/工作/宠物）首次即入库；显式记忆（"记住 X"）不受限 |

### 3.3 一个重要的分层教训（本轮踩的）

第一版把"二次确认"放进了 `_apply_facts` —— **直接打挂 6 个既有记忆测试**
（遗忘 / 衰减 / 归纳都依赖"调用即写入"的契约）。

修正：`_apply_facts` 是**写入原语**（契约不变），确认门 `_gate_facts` 放在**调用点**
（`remember` / `_remember_async`）—— 策略归策略，原语归原语。

**这本身就是 §1 那个结论的又一次印证：改动出问题，往往是把不该放在这层的东西放到了这层。**
