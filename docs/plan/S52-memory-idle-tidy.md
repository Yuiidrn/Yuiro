# S52 · 空闲期记忆整理（后台整理，不占回复时间）

> 需求原话：
> **「在会话间隙与会话结束时触发一轮异步整理，把新写入的记忆与已有条目比对，
> 语义重复的合并归一，相互矛盾的以新替旧，长期无人回顾的压缩成简短摘要，
> 整理过程与会话主链路解耦，不占用回复时间。」**

## 一、与既有三条链路的分工（先划清，避免重复造）

整理这件事项目里**已经有三条链路**，各管一段，本次是补上缺的那一段：

| 链路 | 维度 | 做什么 | 时机 |
|---|---|---|---|
| `forget`（S13） | **时间** | 过期就删（事实/情景各有保留期） | 6h 兜底循环 |
| `consolidate`（S28） | **L2 → L3** | 反复出现的升级为**稳定画像**（支持度门槛） | 6h 兜底循环 + 手动 |
| `_apply_facts` | **L3 冲突消解** | 同 key 同值 NOOP / **同 key 变值 UPDATE（以新替旧）** / 新 key ADD | 每次写入 |
| **`tidy`（本次）** | **L2 内部** | **重复归一 + 冷门压缩** | **会话间隙 / 会话结束** |

★ 因此需求里的"**相互矛盾的以新替旧**"在 L3 侧**早已实现**（`_apply_facts` 的 Mem0 式
ADD/UPDATE/NOOP），本次不需要重做 —— 只需要把整理**接到会话生命周期**上，并补上
L2 内部的"减法"。

## 二、触发：`MemoryIdleScheduler`（`memory/idle.py`）

| 信号 | 来源 | 含义 |
|---|---|---|
| `note_activity()` | `/ws/control` **每轮回复发出之后** | 开始计"会话间隙"（期间又说话则重新计时） |
| `note_session_end()` | `/ws/control` 连接关闭 | "这一场聊完了"，延迟一小段再整理 |

三条约束（与 consolidation 同源）：

1. **不占回复时间**：`note_activity()` 是**同步、O(1)** 的 —— 只重置一个计时器，
   整理跑在它自己的 task 里；聊天链路从头到尾不 await 它；
2. **单飞 + 最小间隔**：同一时刻只有一轮；两次整理间至少 `min_interval_s`（默认 5 min），
   否则"用户连发几条消息"会触发好几轮全库扫描；
3. **失败静默**：整理出错只写日志，绝不影响对话。

## 三、整理内容：`MemorySystem.tidy()`

### ① 语义重复 → 合并归一
用 sqlite-vec 找每条最近的**其它**条目，距离 < 阈值（默认 0.06 ≈ 余弦 0.94）即判为重复。

**归一 = 去重，只删不写**：保留"信息更全的原话"（更长者；等长则更早者），
删掉其余。**不做摘要、不改写** —— 因此不需要重算向量，也就没有"文本与向量不一致"
的风险（那会让检索命中的内容和用户看到的文本对不上）。

### ② 长期无人回顾 → 压缩成简短摘要
条件**缺一不可**：`ts` 够老（默认 45 天）**且** `access_count == 0`（从没被检索命中过）。
条数 ≥3 才压：LLM 只做"压缩"（prompt 明令不添加、不评价、不补全），摘要**沿用最早的 ts**
（否则它会凭空跳到时间线最前面），原条目四表齐删。

> 只看年龄 → 会压掉"很久以前但常被想起"的事（最该留着的）；
> 只看访问次数 → 会压掉刚写下、还没机会被检索的新记忆。

## 四、两个必须强调的实现判断

### ★ 前置条件：`access_count`（本次新增两个迁移）
原表 `messages(rowid, text, ts, salience)` **根本没有访问计数** —— 也就是说，
"长期无人回顾"这个判断此前**无数据可依**。本次加：
`005_message_access_count` / `006_message_last_access`，并在 **`retrieve` 命中时
`mark_accessed`** 回写。

⚠ 这一环**必须先接上**：不记的话计数恒为 0，压缩会把**所有**旧记忆都判成"无人回顾"。

### ★ 删除必须四表齐删（S50 的教训，这次直接做进 store 层）
`store.delete_messages()` 一次删 `messages` + `messages_fts` + `messages_vec`。
**放在 store 层而不是各处手写 SQL** —— 手写的那个调用点一定会漏（S50 实测漏了
`messages_vec`，留下 152 条孤儿向量，且新记忆 rowid 会与旧向量错位关联）。

## 五、安全阀一览

| 项 | 默认 | 为什么 |
|---|---|---|
| 重复判定距离 | **0.06**（偏紧） | 宁可少合，不可把"两件不同的事"合成一条 |
| 冷门年龄 | 45 天 | 太短会把"最近没聊到"误当冷门 |
| 冷门访问上限 | **0 次** | 只要被想起过一次就不算冷门 |
| 压缩最少条数 | 3 条 | 两条不值得压，反而丢细节 |
| 单轮上限 | 合并 20 / 压缩 30 | 防止一轮把记忆库大改 |
| 无 LLM 时 | **不压缩** | 宁可不动，也不用粗暴截断冒充摘要 |

## 六、验证

新增 `tests/test_memory_tidy.py`（6 项，1.32s）：

- 完全相同两条 → 归一，且 **messages/fts/vec 三者同步收敛**（不留孤儿）；
- 近乎重复但不等长 → **保留信息更全的原话**（不改写）；
- 够老 + 从没被想起 + 3 条 → 压成 1 条摘要，原条目删净；
- **反向护栏**：被 `mark_accessed` 过的旧记忆 **不会**被当冷门压掉；
- 调度语义：**间隙期间又说话 → 本次不算间隙**（重新计时）；
- 单飞 + 最小间隔：连发信号只跑一轮。

相关面回归：`55 passed / 1 failed`（那 1 个是既有的 BGE-M3 环境相关失败，与本次无关）。

## 七、知识库：`docs/init/milestones.md` 是怎么变成"她的知识"的

用户发现闲聊时她会冒出"我们在 M4→M5 阶段"这类话，怀疑知识库里装了项目文档 —— **实测证实**：

```
知识库 9 块，全部来自：docs/init/milestones.md
  [里程碑路线图] 当前处于 M4 → M5 过渡（M0–M3 已完成）
  [M0 架构骨架] … [M5 情感/主动/养成（当前）] … [M6 打磨+研究]
  [迭代节奏建议] 每个里程碑一个 git tag；每模块独立 PR
```

**它每轮对话都在注入**（用户日志里的 `knowledge:286 tokens` 就是它）。

### ★ 根因：`KnowledgeStore.clear()` **第二次犯了 S50 同款错误**
```python
conn.execute("DELETE FROM knowledge_chunks")
conn.execute("DELETE FROM knowledge_fts")     # ← 少了 knowledge_vec
```
实测清除前 `knowledge_vec` 有 9 条 —— 也就是说**以前调过一次清除 API，就会留下 9 条孤儿向量**
（语义检索仍可能命中；清空后新导入的 rowid 会与旧向量错位关联）。已修 + 补测试
（知识库此前**一个测试都没有**，所以这个洞一直没暴露）。

### ★ 更深的根因：**后端有、界面没有**
`LIMITATIONS` 里原话就写着"知识库导入/查询后端已具备，调试台暂未提供入口" ——
于是**里面装了什么、每轮注入多少 token，用户完全看不见**。东西悄悄堆进去，直到出戏才发现。

**三处修复**：

| 改动 | 作用 |
|---|---|
| `KnowledgeStore.sources()` + `GET /api/knowledge` 返回来源清单 | 让"装了什么"可见（此前只有一个块数） |
| 新增 `KnowledgePanel.vue`（「记忆」页） | 查看来源/样本、导入、清空 —— 可见可控 |
| **导入防线** `_looks_like_dev_doc()` | 路径像仓库开发文档（`docs/init`/`spec`/`plan`/`features`、milestones/roadmap/architecture/changelog/里程碑/路线图）→ **默认拦住**，提示"会每轮注入对话、容易出戏"，确需导入带 `force` |

**★ 判断规则**：**能力"存在"不等于"可管理"。** 任何会持续影响运行时行为的数据
（记忆、知识库、缓存），都必须有**查看与清除的入口**；否则它必然积累成一个
"没人知道里面是什么、却一直在生效"的黑箱。

## 八、「记忆」页重排 + 术语人话化

用户原话：**「什么 L2、L3 这种注释表述不要出现在标题栏里而让人看得云里雾里」**。

### 顺序：先看 → 再看你给的 → 再管 → 最后调参
此前是「洞察 → 参数 → 管理」，参数夹在中间 —— 想查一条记忆得先滚过一堆数字输入框。
现在：**记忆洞察 → 知识库 → 记忆管理 → 记忆行为（参数）+ 记忆归属**。

### 术语对照（界面上一律不出现 L2/L3/RRF 这类内部词）
| 原表述 | 改为 |
|---|---|
| 稳定事实（L3） | **她记住的你** |
| 近期情景（L2） | **聊过的片段** |
| 显式记忆 | **你让她记住的** |
| 用户事实（L3） | **她记住的你** |
| L3 事实隔离键 | **记忆归属**（"这些记忆算在谁名下"） |
| RRF k | **融合平滑参数**（+说明"融合四种检索信号的系数，一般不用改"，并移入「高级」） |
| 后端 / 嵌入模型 / 注入阈值 | **存储方式 / 语义模型 / 相关度门槛**（各补人话 hint） |
| 支持度 N | **提到过 N 次** |
| "扫描 N 条情景 → 候选 M → 低支持跳过…" | **"翻看了 N 条聊过的片段，归纳出 M 条新的印象（X 条因为'只提过一次'没有采纳）"** |

**★ 判断规则**：界面上面向用户的字段，**标题必须是"用户能用自己的话讲出来"的**；
内部代号（L2/L3/RRF/支持度）只该出现在代码与开发文档里。判断标准：把标签念给
一个没用过这项目的人听，他能说出"这是干什么的"吗？
