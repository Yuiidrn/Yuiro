# S42 · 架构收口（P0-A / P0-B / P1）

**触发**：用户质疑 —— "我们一直是拆东墙补西墙，点到一个问题解决一个问题，做不到泛化性和稳定性"。

这个判断被 S18→S41 的路径**验证了**：每一次都是「发现一个具体问题 → 补一条具体规则或标志」，
修好眼前，不产生泛化。本 Sprint 不再修具体功能，而是**把知识放回正确的层**。

## 一、诊断：为什么越修越脆

| 知识类型 | 正确位置 | 改造前 |
|---|---|---|
| 单个工具怎么用 | 工具的 `description` | ✅ 早已很好 |
| 工具之间的选择/冲突 | 提示词（跨工具段） | 🟡 埋在 28 行具体例子里 |

## 二、P0-A：`TurnState` —— 把推进策略从散落布尔里收回来

**改造前**：`AgentLoop.send()` 里平铺着 9 个状态变量

```
task_nudges / task_nudge_line / last_task_line / write_nudges /
write_nudge_pending / wrote_anything / claim_nudges / claim_nudge_pending /
round_tool_results
```

它们其实只描述**三个同构的"推进策略"**（任务续跑 / 写操作后续跑 / 幻觉纠错），
每个都是「计数 + 上限 + 待注入提示」。

**平铺的真实代价**（不是"不优雅"，而是直接导致打地鼠）：

1. **加一个策略要在 200 行循环里改 5 处**（声明、注入、判据、计数、日志）——
   漏一处就是"提示注入了但没生效"或"计数器永远不到上限"这类难查的 bug；
2. **判据埋在 async 生成器里，无法单测** —— 只能靠真机跑对话看日志；
3. **状态看不全** —— 调试得 grep 才知道有几个标志在影响流程。

**改造后**（新模块 `agent/turn_state.py`）：

```python
st = TurnState()                 # 三个 Nudge：task(3) / write(3) / claim(1)

for _nudge_text in st.injections():        # 注入：一个循环，顺序 + 清空由状态保证
    messages.append({"role": "system", "content": _nudge_text})

st.add_tool_result(llm_result[:2000])      # 记录
st.wrote_anything = True

if st.task.can_push() and (...):           # 判据：可单测
    st.task.push("（任务续跑）当前进度：…")
```

**净效果**：`send()` 少 **60 行**，新增策略 = 加一个字段 + 一段文案。

**行为等价性**：默认上限 `(3, 3, 1)` 与本重构前的硬编码一致，并有测试钉住
（`test_default_limits_match_historical_behaviour`）。

## 三、P0-B：`PendingInteraction` —— 让"等用户选"可点、可过期

**改造前**：`StateNotes` 里的 pending 是一个**裸字符串**。

三个具体损失：

1. **选项会丢** —— 歌单候选 / 点歌版本这类"让用户挑"的场景，引擎其实知道有哪几个
   选项、各自的 id 是什么，但字符串里只能塞一句"请从下面选一个"。
   前端拿不到可点的东西，只能让模型复述一遍（S41 就卡在这儿）。
2. **TTL 不能分类型** —— "扫码登录"可能等几分钟仍有效，"选歌版本"几轮不答就该失效；
   单槽 + 固定轮数做不到。
3. **判据不可测** —— 原来"还有没有在等"等价于 `bool(str)`。

**改造后**：

```python
@dataclass
class PendingInteraction:
    question: str
    kind: str = "confirm"              # confirm | choice | login
    options: list[dict] = ...          # ★ 选项一路传到前端点选
    expected: str = ""
    turns: int = 0
    ttl_turns: int = 3                 # ★ 按交互类型给不同 TTL
```

`set_pending` / `pending` **签名不变**（agent 循环、ContextEngine 全部无需改动），
新增 `set_interaction` / `interaction`。前端点选部分由 S41 的 `agent.result` 卡片承担。

## 四、P1：工具返回规约（`tools/result.py`）

**改造前**：每个工具自己拼 JSON，字段名各不一致（`playlists` / `options` / `items` /
`tracks` / `songs` / `list`…）。引擎想把结果变成用户看得见的东西，只能靠一张**硬编码
字段名映射表**（`_RESULT_CARD_KEYS`）。后果：

- 新工具用了新字段名 → 界面上什么都不显示（用户侧 = "给了个壳、没有反馈"）；
- 想加一种反馈形式得回去改引擎的映射表。

**改造后**统一为：

```json
{
  "status": "ok|error|pending|need_choice",
  "message": "给人看的一句话",
  "options":   [ {"name": ..., "id": ..., "note": ...} ],
  "artifacts": [ {"path": ..., "note": ...} ]
}
```

配 `ok() / err() / pending() / need_choice()` 四个辅助函数。

**并有一条交叉验证测试**（`test_engine_recognizes_the_options_field`）：
规约字段必须真的出现在引擎的 `_RESULT_CARD_KEYS` 里 —— 防的是最隐蔽的失配
「规约更新了但引擎没跟上」，那种 bug 只能从用户侧"怎么没反应"倒查。

## 五、顺带修掉的两个静默故障

### 1. 提示词有三份副本，而且已经不同步

| 位置 | 改造前 | 改造后 |
|---|---|---|
| `config.toml` | 28 行、点名 12 个工具、6 段示例对话 | 注释掉（用内置） |
| `agent/__init__.py` | 40 行 | **4 条原则**（21 行） |
| **`config.py` `PersonaConfig`** | **35 行，仍在教模型用废弃的 `media_control` 控制网易云** | 留空（唯一真相源） |

**关键**：`config.py` 那份非空 → `_DEFAULT_SYSTEM_PROMPT` **从来没被用过**。

新原则（不含任何工具名）：**先做再说 / 如实 / 自己想办法别撞墙 / 领域边界**。
其中"歧义就把候选摆出来让 Yui 挑"是 S41 的教训**抽象成原则**的产物。

护栏测试（`tests/test_agent_prompt.py`）：长度上限、**不许出现工具名**、
**不许出现示例对话**、四条原则必须在。

### 2. BGE-M3 权重缺失导致语义检索静默降级数周

- 缓存里 4.32GB 全是 `.incomplete` 分片，**只缺 `pytorch_model.bin`**；
- `Embedder` 缺权重时**静默降级到 md5 向量**（无语义，相似度≈随机）；
- `config.toml` 被改成了 `embedder = "md5"`（等于放弃）；
- **引擎启动从不体检** → 唯一的信号是"感觉记忆不准"。

补齐过程中踩的三个坑（都已写进 `scripts/fetch_bge.py`）：

| 坑 | 解法 |
|---|---|
| HF 主站 DNS 失败 | `HF_ENDPOINT=https://hf-mirror.com` |
| 新版 hub 用 Xet 存储，镜像不支持 → 401 | `HF_HUB_DISABLE_XET=1` |
| 只补缓存不够：transformers 校验**整个 snapshot**，缺 onnx 就拒载 | 下到**本地目录**，走本地加载路径 |

并加了 **`main.py` 启动自检**（`_probe_embedder_files`，纯文件检查、不 spawn 子进程）
—— 这类"静默降级"以后会在启动日志里一眼可见。

**实测**（真实账号 53 个歌单）：

| 查询 | 结果 |
|---|---|
| 助眠 | 《做个好梦.》（0.67） |
| 跑步 | **《运动》（0.73）← 字面完全不同，泛化的直接证据** |
| 我喜欢的音乐 | 《I_drcen喜欢的音乐》（0.81） |
| 学习 | 候选（"自习室"与"六级词汇"都相关）→ **正确地不猜** |

## 六点五、facts 存量清理（S40 闸门的补课）

S40 的四道闸门**只管新增** —— 存量污染仍躺在库里，而且每一轮都在参与注入。
实测 9 条里有 4 条有问题：

| 记录 | 问题 | 处理 |
|---|---|---|
| `用户/名字 = 什么名字` | 值是问句残留；且 **subject 与 `[persona].memory_subject` 不符** → 检索按 subject 过滤，**永远查不到（死数据）** | 删 |
| `用户/喜欢 = 吃火锅` | subject 不符 + key 太泛（"喜欢"什么？值才是答案） | → `Yui/饮食偏好 = 吃火锅` |
| `审美风格 = 老派浪漫` ⟷ `音乐偏好 = 老派浪漫风格` | 同义重复，白占两份注入预算 | 删前者 |
| `歌曲偏好 = 《谁》Live版` | 把**一次性事件**记成稳定画像 | 删 |

清理后 **6 条**，全部 `subject=Yui`：

```
饮食偏好=吃火锅 · 听歌习惯=喜欢跳过前奏直接听主歌部分 · 歌曲版本偏好=Live版
音乐偏好=老派浪漫风格 · 常用音乐应用=网易云音乐 · 籍贯=广东
```

脚本 `scripts/clean_facts.py`（`--dry-run` 预览 / `--apply` 执行并自动备份）。
**规则全部显式列举、不做启发式** —— 动用户数据必须可解释、可复核；
且实现上刻意做了两个保守选择：目标键已存在时**跳过不覆盖**、预览与执行分离。

> 值得记下的教训：S40 修的是**入口闸门**，"存量清理"是**另一件事**。
> 加了闸门不等于库就干净了 —— 这类「修了入口、忘了存量」的盲区，
> 值得在每一次数据卫生改动里都主动问一句。
